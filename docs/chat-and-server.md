# Conversations, the server, and the chat interface

[Back to the README](../README.md). Talking to the head of a lab, the server that a page talks to and its API, and building and running the chat interface.

## Talking to the head of a lab

A meeting is run to a plan. A `Chat` is the other way round: you talk to one agent, the lead, and it answers directly when it can. When the answer needs a computation it runs code in the session, and when a question needs more than one kind of expertise it brings the team in, through two tools it is given:

- `convene_team`: several scientists of the team discuss an agenda with the lead leading, and the lead is given the summary they reached.
- `consult`: one scientist works on an agenda with the Scientific Critic reviewing, and the lead is given its answer.

```python
from virtual_lab import Chat, LocalSession

with LocalSession(Path("work")) as session:
    chat = Chat(
        Path("chats/example"), lead=principal_investigator,
        team=(immunologist, ml_specialist, scientific_critic), session=session, max_cost=5.0,
    )
    counts = chat.save_upload("counts.csv", open("counts.csv", "rb"))
    reply = chat.send("Which genes are higher in the treated samples?", attachments=[counts])
    print(reply.status, reply.text)
```

- These are meetings, held as a `Project` holds them, in the conversation's directory under `lab/`: they run in the same session, get the same resources and tools, are saved and counted the same way, and count towards the same `max_cost` as the lead's own requests, in every run of the conversation on that directory. The lead may start `max_delegations` of them in answering one message, and asks for at most `max_rounds` rounds of each, so a question cannot run up a bill the researcher did not expect. A model that sends the same request twice in one message, as some do when they call tools in parallel, has it held once: the second is answered with "Not held again" and costs nothing. Without a team, or with `max_delegations=0`, the lead works alone. Without a `session` nobody runs code.
- A turn ends `answered`, `stopped`, or `failed`, as the `ChatReply` says. A failure is reported there and as an event, not raised, and the conversation goes on from it. When the model provider is the cause (a key it refuses, an account out of credit, a rate limit, a provider that is down or cannot be reached, a conversation too long for the model, a reply with nothing in it, or the provider's own safety check stopping the conversation, which says to use Edit on the last message, since what was flagged stays in the conversation), the text says so in plain words with what to do about it, followed by the provider's own message, shortened, in brackets; any other failure is told as `Type: message`, and the event's `type` is the error's class either way. `send` waits for the answer, and `start` answers in a thread of its own, to be followed through the events.
- Files are attached with `save_upload`, which keeps one under a name that is safe whatever it was uploaded as, never replaces another, and refuses one larger than `max_upload_bytes`. They are saved in the session's `uploads/`, where its code reads them, and the lead is told what was attached. `resources` is as for a meeting: the lead is told of Biomni's tools, data lake, libraries, and know-how, by default through a `find_resources` tool that asks which of them suit a task, and the team is told of the same.
- Everything that happens is a `ChatEvent`, numbered in order: the message, each reply as it is written with `stream=True`, each tool call and its output, each run of code with where its figures are, what the team does, notes, and usage, and how the turn ended. `on_event` is called with each, and `events_since(n)` and `wait_for_events(n, timeout)` give what has happened after number `n`, so a page that reconnects catches up from the last one it saw without missing any. The state the conversation is in, and the reply being written, are the latest of each, not what they were as they changed.
- `on_event` is called in the thread that caused the event, with none of the conversation's locks held, so a slow callback holds up only its own thread. Events from different threads can reach it out of order, and their number is the order they happened in. An exception it raises ends the turn like any other failure, except when it is told how the turn ended or what state the conversation is in, which is only warned about, so a callback for a page that went away cannot leave the conversation running.

```python
thread = chat.start("Which pathways are enriched in the treated samples?")
last = 0
while thread.is_alive():
    for event in chat.wait_for_events(last, timeout=1):
        last = event.id
        if event.kind == "lab":
            print(f"[{event.data['meeting']}] {event.speaker}: {event.text}")
        elif event.kind == "answer":
            print(event.text)
```

- The researcher steers from any other thread. `add_note` gives the lead, or the team if it is working, a note to read before it goes on. `pause` holds the turn before its next request, or the team's next turn, until `resume`. `stop` ends it at the next point it can be, with what was done kept and every tool call answered, so the next message starts from a valid conversation; code or a tool that is running is not interrupted, but a request that is waiting for a model is given up on at once, so a provider that says nothing cannot hold a conversation (the request is left to end as it will, and its reply is dropped). `close` stops a turn and ends waits on the events.
- `set_limits(max_cost=..., max_delegations=..., max_rounds=...)` changes what a conversation may spend and what the lead may ask of the team, whether or not a turn is running (leave out what is to stay as it is; `max_cost=None` takes the limit away). The new spending limit holds from the lead's next request, and a `usage` event tells the pages of it. `max_delegations` (at most `CEILING_CHAT_DELEGATIONS`, 20) and `max_rounds` (at most `CEILING_CHAT_DELEGATION_ROUNDS`, 10) are used from the next message, which is when the lead is given its tools again; `max_delegations=0` has it work alone. Changing the spending limit of a conversation whose model has no known price raises `CostUnknownError`, as giving it one does. The limits are kept in `chat.json`.
- The conversation is saved as it goes in its directory: `chat.json`, `messages.jsonl` (what the lead was sent and said), `events.jsonl`, `uploads/`, and `lab/`. A `Chat` opened on the same directory carries on from there, with the same title, usage, and messages and the same numbering of events. If the process was killed during a turn, that turn is ended as `Interrupted` when the conversation is opened.
- The lead may call tools, and run code, `max_tool_iterations` times in answering one message (20 with a session, 5 without). On its last request it is given no tools and is told so, to say what it has done, what is left, and what it would do next; the researcher writes "continue" to give it more. With `check_results=True` (a conversation made by the server has it unless its request says `check_results: false`), a lead that ran code for a message and then wrote an answer is asked once, before the researcher is given it, to check the result: that it is the quantity asked for, its sign and direction (a quantity where smaller means stronger, such as a p-value or a rank, is not "higher is more" until it is flipped), the filters, thresholds, and background that went into it, its units and scale, the data that went in (how many rows, repeated or mismatched identifiers, missing values), and whether it is plausible, with a second way of getting the number run where there is one, and to say which choice it made where the message leaves one open. What it wrote first stays in the conversation as something it said, and what it writes after is the answer. It costs one more request, and whatever the checks run, for each message that ran code; it is not asked on the last round, which has no tools, nor when no code ran. The lead is told to keep each check short and in the foreground, with no background job (`nohup`, `&`) and no rerun of the whole analysis, and the checks have `CHECK_TOOL_ROUNDS` (6) rounds of tool calls, never more than the message has left: on the request after the last of them it has no tools and is asked for its answer again, and not for how far it got. If it still writes only calls out as text after being told that nothing ran, the researcher is given the answer it wrote before the check. A model that writes a call out as text instead of making it, which a model does that is shown its own earlier calls as text, has called nothing: it is told that nothing ran and asked again, up to `MAX_FAKED_CALL_RETRIES` times in a message, and that does not use up one of its rounds. If it will not stop, the answer is what it wrote besides the calls, or else a plain message saying so, never the text of a call.
- `Chat(campaign=CampaignBrief(name, brief))` tells the lead, in every message it answers, that the conversation is one of a campaign of conversations that work toward one goal, and what the goal is, before any instructions of the conversation's own. `set_campaign(...)` changes it, or takes it away with `None`, and holds from the next message, since what the lead is told is put together once for each. The team's sessions are not told of it directly: the lead decides what of it to put in the agenda it writes.
- A conversation that has outgrown what the lead's model can read says so, in an error that names what to do, rather than being sent to fail. `max_cost` is checked before every request, so it can be overrun by the cost of one, and a model with no known price cannot be given one.

### Serving the conversation to a page

A page talks to a `Chat` through a server, which keeps each conversation under `chats/` in the workspace, runs its code in the session the settings choose, and tells the page of every event as it happens. It needs FastAPI and Uvicorn, which the `server` extra installs.

```bash
pip install -e ".[server]"
virtual-lab-server                      # http://127.0.0.1:8765, or the first free port after it
virtual-lab-server --workspace ~/lab --port 9000 --no-browser
```

```python
from virtual_lab.server import serve

serve(workspace="~/lab", port=9000)     # waits until stopped
```

It prints a link with a token in it. Opening the link keeps the token in a cookie, and takes it out of the address.

- The server is for one person. Anyone who reaches it can spend on your keys and, where code runs, run code on your machine, so it answers only a request that names this machine in its Host header, as a name and a port and nothing else (which turns away a page at another address that was made to point here), wants the token for everything under `/api` but `/api/health` (as the cookie, or as `Authorization: Bearer`), and turns away a request that changes anything and comes from a page of another address. Each page of the interface carries a Content-Security-Policy that lets it run only the scripts in its own files and the few written into the page, which it names by their hashes (worked out from the page when it is served), and lets it load and send nothing to another address, so that nothing a model writes can become a script. Listening beyond this machine with `--host` is refused unless `--allowed-host` names what it is reached by, and it says so when it starts. `--token` or `$VIRTUAL_LAB_SERVER_TOKEN` sets the token; otherwise one is made for each run.
- The keys you give the page are kept in this machine's own keychain (the macOS Keychain, the Windows Credential Manager, or the Secret Service), through the `keyring` package, under the service `virtual-lab` with the name of the variable as the account, so that they are there when the server is started again. They are written nowhere else, and anyone who can unlock your keychain can read them. A key in the environment the server is started with, such as an `OPENAI_API_KEY` exported in your shell, is used before one kept, and is never stored. `--no-keychain`, or `serve(keychain=False)`, keeps keys only until the server stops. Where there is no keychain, such as a Linux machine without the Secret Service, the page says so and keeps them until the server stops. The keychain has 5 seconds to answer, since a locked one can wait for you to unlock it, and one that does not is said to be locked rather than waited for. The tests never reach the machine's keychain: they are given one that is a dictionary.
- Every route is under `/api` and answers in JSON, and an error answers `{"error": {"code": ..., "message": ...}}` with a code a page can act on: `missing_keys` (422, naming which keys), `setup_needed` (409, naming what is `missing`: `docker`, `image`), `docker_unavailable`, `already_built`, `busy`, and `closed` (409), `too_large` (413), `not_found`, `invalid` (422), `unavailable` (422, for a conversation whose saved files cannot be used, naming the file and what is wrong with it), and `files` (500, when a file or directory of the workspace cannot be read or written, naming it and why, such as a workspace that is read-only).
- `GET /api/chats` lists the conversations (each says its `kind`), `POST /api/chats` starts one (`kind`, which is `quick_task` unless it is `custom`, a program with a name of its own, which is its `title` and is required, and `instructions`, up to 8,000 characters, that the lead is given with every message and that a custom program must have and no other may, kept in the conversation's `config` too, or `build_skill`, a program for building a skill, which needs code to run (422 with where to turn it on if the settings or the request have none) and is given the tool that saves a skill, as [Skills](tools-and-skills.md#building-a-skill-with-the-lead) says; the model, the lead, the team, where code runs, the budget, how many team sessions the lead may start for a message and how many rounds each may have, how many tool calls and runs of code it may make for a message (`max_tool_iterations`, 1 to 200, which is 20 where code runs, and is kept in the conversation's `config`), whether the lead checks its results before answering (`check_results`, true unless it says false, kept in `config` too), and whether to stream, each taken from the settings or the library if left out), and `campaign`, the id of the campaign it is to be part of, which must exist and is kept in `config` too, and the list says which campaign each is part of, or `null`), and `GET`, `PATCH`, and `DELETE /api/chats/{id}` show, rename, and remove one. `PUT /api/chats/{id}/campaign` with `{"campaign": id}` makes a conversation part of a campaign, or with `{"campaign": null}` of none, whether it is closed, idle, or at work: the lead is told the goal from its next message, and nothing else is changed. `POST /api/chats/{id}/close` closes one that is open, ending its turn if one is running and freeing its session, so its container, while what it saved is kept (204; 404 for one that is not there), which a program that asks one server many questions can do after each, since a container stays up with what it loaded until then. A conversation that was saved is opened again when it is asked for, with its events numbered as they were. One whose model's key is not set can be read, and is asked nothing until the key is set.
- `POST /api/chats/{id}/messages` answers at once (202), and the answer comes as events. With `"replace_last": true` the message takes the place of the last one, to send it again or changed: that message and all that came of it are taken out of the conversation and its saved files, and a `withdrawn` event tells of it just before the new `user` event, which begins the same turn again. What the turn did to the session and to the lab's files is not undone. `note`, `pause`, `resume`, and `stop` steer the turn that is running, and say whether they could. With `"directive": "ask"` (or `plan`, `search`, `code`, `plot`, `review`, `lab`) the message goes with a command that says how to answer it: `ask` and `plan` answer without tools, `search` reads the literature first and cites it, `code` and `plot` run code, `review` has the Critic go over the last answer (it takes no text of its own, and the others need some), and `lab` has the lead hold a team session that the researcher has set up: `"lab": {"mode": "team" | "individual", "members": [titles from the library], "rounds": 0..max_rounds, "questions": [at most 10]}` says who takes part (one scientist, who the Critic reviews, for `individual`), and the lead is given only the tool for that session, with who and how many rounds fixed, so that it writes the agenda and its answer follows from what the session found. Scientists who are not on the conversation's team are added to it first, once the rest of the request has been checked (a `/lab` that is refused leaves the team as it was), which needs the lead not to be at work (409 `busy` otherwise), and a title that is not in the library is refused (422); `lab` is accepted only with that command, which needs it. A command the conversation cannot carry out is refused before anything is sent (`invalid`, 422, saying why: `code` and `plot` need code to run, `search` needs a literature tool, `review` needs the Critic, team sessions, and an answer to review), and `directives` in a conversation's info says which can be used now and, for those that cannot, why. The command (and `lab`, for `/lab`) is in the `user` event's data, is replayed when the message is sent again, and, for the commands that have something to check, the `answer` event's data says in `directive_met` whether the lead did what was asked (for `lab`, that a team session was held), after one reminder if it had not. A message can instead be given with `"skill": "NAME"`, one of the conversation's skills (matched without regard to case, and written as `/NAME` in the interface): the lead is told beside the message to read it first with `activate_skill` and follow it, and if it answers without having, it is reminded once, and `directive_met` says whether it read the skill. A skill is not given with a `directive`, needs text written with it, and one the conversation does not have is refused (`invalid`, 422); it is in the `user` event's data as `skill`, and is replayed when the message is sent again.
- A campaign is a name and a goal that programs share, kept in `campaigns.json` in the workspace. `GET /api/campaigns` lists them (each with `id`, `name`, `brief` (the goal), and `created_at` and `updated_at`), and `POST /api/campaigns` with `{"name": ..., "brief": ...}` makes one (at most 80 characters for the name, which is kept with its words one space apart, and 8,000 for the goal, which may be empty and then tells the lead nothing; at most 200 campaigns, and no two with the same name, whatever the case: `exists` and `too_many`, 409), answering 201 with the campaign as `GET /api/campaigns/{id}` shows it, which is also its `programs` (the conversations that are part of it, as the list of conversations gives them) and what they have `spent` between them. `PATCH` changes its name or goal (422 if it has neither), and `DELETE` removes it (204) and leaves its programs, which are then part of none. A conversation is part of at most one campaign. A conversation that names a campaign that is not there, which a hand-edited file can, is treated as part of none. The conversation's `config`, in `GET /api/chats/{id}`, says which campaign it is part of as `campaign`, which is `""` for none.
- `GET /api/chats/{id}/events` is a stream of server-sent events, each with its number as its `id`. It starts after `?after=` or the `Last-Event-ID` a browser sends when it opens the stream again, whichever is later, so a page that was cut off misses nothing. The server keeps nothing for a stream: it reads the conversation, so a slow page is told of the latest of a reply being written, and not of every word.
- `POST /api/chats/{id}/uploads?name=...` takes a file as the body, and gives back what `save_upload` does, to name in the next message. `GET /api/chats/{id}/files` lists what the conversation made or was given, and `/files/{path}` sends one. A file the agents' code wrote is never run by the page: HTML and scripts are sent as plain text, only types that are safe to show are shown in the page and the rest are saved, all with a CSP that runs no script and fetches nothing from elsewhere, and a path that leaves the conversation's directory is not a file.
- `GET` and `PATCH /api/settings` show and change what each new conversation starts with, `GET /api/models` lists the models (with a few of OpenRouter's) and whether their keys are set, `GET /api/models/openrouter` lists all the models OpenRouter serves that can call tools, each with its name, context length, and prices per million tokens (`models`, and a `problem` if the list could not be fetched, in which case the last one fetched is given if there was one), and `PUT /api/chats/{id}/limits` with any of `{"max_cost": ..., "max_delegations": ..., "max_rounds": ...}` changes a conversation's limits where it is, even while it works (an empty body is `invalid`, 422, as is a number past the most, which `chat_limits` in `/api/settings` gives with the defaults; a spending limit on a model with no known price is `unavailable`, 422), and `PUT /api/chats/{id}/model` with `{"model": ...}` has a conversation go on with another model from where it is (what was said and its files are kept, and code that was running starts afresh; `busy`, 409, while it is working, `missing_keys` or `unavailable`, 422, when the new model's key is not set or, with a spending limit, its price is not known), and `GET /api/keys` says which providers have theirs, where each key that is set came from (`sources`: `keychain`, `session`, or `environment`), and what keychain the server has (`keychain`: whether it is `available`, its `name`, and a `problem` if there is none to use, or the keys kept in it could not be read when the server started). `PUT /api/keys/{name}` sets a key and keeps it in the keychain, unless the body says `"remember": false`, which keeps it until the server stops and forgets one kept before. A keychain that will not keep it does not fail the request: the key is set until the server stops, and `problem` in the answer says why. `DELETE` takes a key away, from the keychain too, and says in `problem` if the keychain would not forget it. A key is never written to the workspace or sent back. `/api/scientists` keeps the scientists you describe, in `scientists.json` in the workspace.
- `GET /api/skills` lists the skills found, with whether each is on and whether it can be removed (only a skill in the workspace's own `skills/` folder can, and not one that comes with the lab, which has `source` `builtin`), what was wrong with a `SKILL.md` that could not be used, and the folders searched. `PUT /api/skills` takes `{"disabled": [...]}`, which `skills.json` in the workspace keeps, so that a skill added later is on; a conversation is given the skills that are on when it is made, or the ones `skills` names in `POST /api/chats`. `POST /api/skills/install` takes either `{"git": "https://..."}`, an `https` address of a repository, which is cloned (one level deep, with no credentials asked for, and links not followed, and stopped if it takes more than 5 minutes or 1 GB), or `{"path": "/folder"}`, one on this machine (searched in at most 5,000 folders), and copies each skill found into the workspace's `skills/` folder, leaving a skill whose name is taken as it is and saying so. `POST /api/skills/upload` puts in skills from a folder that is sent to it, as a `multipart/form-data` form with a `folder` (its name), a `paths` field for each file (where it is in the folder, such as `scripts/fit.py`), and a `files` field for each, in the same order; a path that leads out of the folder, a path given twice, more than 2,000 files, or more than 50 MB is refused (a request that does not give its length, as one sent in chunks does not, is refused with 411), folders such as `.git` and `node_modules` are passed over, and what is put in, and what is left and why, is said as for `install` (a folder with a `SKILL.md` at its top is one skill, and one without is searched for them). `GET /api/skills/{name}` gives the instructions and the files of a skill, to read before it is trusted, and `DELETE /api/skills/{name}` removes one from the workspace's folder (never from `~/.agents/skills`). The Skills page (`/skills`) shows the same, with a search box and a warning to trust only what you would follow. `catalog` says what listing the skills that are on takes of every request (`skills`, `chars`, `budget`, the `description_chars` each description is cut to, and how many skills are listed by name alone, `without_description`). Where a conversation begins, the Skills button beside the model (or `/skills`) chooses the skills that one is given, in place of those that are on, and sends them as `skills`; in a conversation, `/skills` shows the ones it was given, which its `config.skills` names, and which it keeps from its start.
- `GET /api/tools` lists the library's tools that the lead of a conversation can be given, by what they are for (literature, the web, proteins and structures, chemistry, and the files you attach), and whether each is on; `PUT /api/tools` takes `{"disabled": [...]}`, which `tools.json` in the workspace keeps, so that a tool the library gains later is on. A conversation is given the tools that are on when it is made, or the ones `tools` names in `POST /api/chats` (a name the library does not have is refused), and its `config` says which. Where code runs, `data_files` and `inspect_data_file` look in the session's directory, and the lead is also given `fetch_structure_file`, which downloads a structure there for code to read. Where none does, those two look at the files attached to the conversation, so that the lead can look inside a table or a spreadsheet without running anything, and `fetch_structure_file` is left out. `view_image` (under "Your files") is given to a conversation whose model reads images, as far as is known: an OpenRouter model that OpenRouter lists as taking images in, an OpenAI model from GPT-4o on, or one of Anthropic's or Google's; a switch of model gives it or takes it away.
- `GET /api/skill-library` lists the 177 scientific skills that come with the lab (see [The Skills Nexus](tools-and-skills.md#the-skills-nexus)): each with its group and category, its license (and `license_kind`, one of `noncommercial`, `copyleft`, `none`, or `other`), how many files and bytes it has, and whether it is `installed` (its name is taken in the workspace's `skills/`), with the categories, where the library came from, and what was wrong with any entry. `GET /api/skill-library/{name}` gives one's instructions and files, to read before it is put in, and `POST /api/skill-library/install` with `{"names": [...]}` copies those skills into the workspace's `skills/` folder, leaves any whose name is taken, and answers as `POST /api/skills/install` does, with `GET /api/skills` as it now is. An empty list, or a name the library does not have, is refused (422) and puts nothing in.
- `GET /api/own` lists the data and software you give the lab to use in every conversation. A piece of data is a file or a folder, found by its file name, so no two have the same name (`name_taken`, 409), and each says what it is in words (`description`, which the lead is told, so that it knows when to use it). `POST /api/own/data/files?name=...&description=...` uploads a file as the body, up to the server's upload limit (`max_upload_bytes` in the answer; a larger one is refused with `too_large`, 413, before it is read if it says how big it is), and keeps it in `own_data/` in the workspace. `POST /api/own/data/paths` with `{"path": ..., "description": ...}` points to a file or folder where it is on this machine, by its full path (or one that begins with `~`), and leaves it there: it is not copied, and giving it up never deletes it. A path where conversations are kept, or that holds them or the uploads, is refused, and so is one Docker cannot mount (a comma, a quote, or a line break in it). `PATCH /api/own/data/{name}` says again what it is, `DELETE` gives it up (an uploaded file is deleted), and `GET /api/own/data/{name}/preview` shows the first lines of a text file, that a file is `binary`, or what is in a folder. Each piece in the answer says where it is (`source`: `uploaded` or `path`), whether it is a `file`, a `folder`, or `missing`, and how big and how recently changed. `PUT /api/own/software` with `{"name": ..., "description": ...}` gives some software and what it is for, and `DELETE /api/own/software/{name}` gives it up; a conversation tells the lead of it, and the lead checks that it is installed where the code runs before relying on it. A conversation is given all of it when it is made, or the `data` and `software` names in `POST /api/chats` (a name that was not given is refused), and its `config` says which. Where code runs, each piece of data is read-only: in Docker at `/data/<name>`, and on this machine where it is. A conversation takes what it is given when the server starts it, and again when it is opened after the server was stopped, so data given later is in new conversations and not in those already going, and what has been given up, or has gone, is left out then rather than stopping the conversation from opening. The web interface's Data page (`/data`) is where these are given, with the data lake beside them. (Skills are on the Skills page, `/skills`.)
- `GET /api/mcp` lists the [MCP servers](tools-and-skills.md#tools-from-mcp-servers) a conversation can be given: the presets, whether or not they are set up, and the ones the person added, each with whether it is on, how it is signed in to or given a key, which keys it is missing and which of the library's service keys are set, whether it has tools that wait for approval, and, if it cannot work as it is, why. `PUT /api/mcp/servers/{name}` sets one up in full from an entry as a config gives it (checked as `connect_mcp` reads it, without connecting), `PATCH` turns it on or off or chooses between a key and signing in for a preset, and `DELETE` forgets it; `mcp.json` in the workspace keeps them. Adaptyv's two presets are not listed until one is set up, since the interface does not offer Adaptyv yet (`NOT_OFFERED` in `server/mcp.py`); they are still presets, which `connect_mcp` and a config can name. `GET /api/mcp/catalog` lists a short catalog of servers that others run (`server/mcp_catalog.py`: each with its title, what it is for, who runs it, its site, where it is reached, whether it asks before a call or is signed in to, and whether it is `added`), and `POST /api/mcp/catalog/{name}` sets one up, on, as `PUT` would with its entry, answering with the servers as `GET /api/mcp` does (`not_found` for a name that is not in it, `exists` (409) if a server is set up under that name, `invalid` (422) past the most servers there may be). A server added from the catalog is listed with its title and what it is for, for as long as it is kept as the catalog describes it. A server that is signed in to with an account says whether it is (`signed_in`, which is `null` where there is no sign-in or its address is not known), and `DELETE /api/mcp/servers/{name}/sign-in` forgets the sign-in, with `invalid` (422) for a server that is not signed in to. `POST /api/mcp/servers/{name}/check` connects to a server as a conversation would, whether or not it is on, and answers `{"ok": true, "tools": [...]}` or `{"ok": false, "reason": "..."}`; it never opens a sign-in page, allows a call, or answers a question, and while a check of the same server is going another is refused with `busy` (409). `PUT /api/keys/{name}` also takes the keys of the presets' services (`PAPERCLIP_API_KEY`, `FOUNDRY_API_TOKEN`, `FOUNDRY_TESTING_TOKEN`) and the web search's (`EXA_API_KEY`), kept the same way. A conversation is given the servers that are on when it is made, or the ones `mcp` names in `POST /api/chats`, and connects to them when its first message is sent, telling of each as a `connection` event (`connecting`, `signing_in` with the address of the sign-in page, `ready` with how many tools, or `failed` with why). A server that cannot be connected to fails the turn before anything is spent, and is tried again with the next message. Before a call to a tool that waits for approval, the conversation tells of an `approval` event (`waiting`, then `approved`, `declined`, or `withdrawn` if the turn ended first), which `POST /api/chats/{id}/approvals/{request}` answers with `{"allow": true|false}`; and what a server asks while a tool runs is a `question` event, which `POST /api/chats/{id}/questions/{request}` answers with `{"answer": {...}}` (checked against the form the server asked for, and refused with `invalid` while it does not fit, with the question still waiting) or `{"answer": null}` to decline. What was answered is not kept in the events. A request that nothing waits for is refused with `not_waiting` (409), and stopping the turn, or ending the conversation, withdraws what waits.
- Settings also say where Biomni's data lake is kept (`data_lake`, a full path, or the workspace's `data_lake/` if empty) and which of the keys the interface can set code is given in Docker (`forward_keys`, which a conversation's `code.forward_env` may replace). A conversation whose code runs in one of Biomni's environments is given the data lake to read, once there is one, and the keys it was told to forward, which are passed by name and never written down.
- `GET /api/setup` says what code in Docker needs and what is there: whether Docker is installed and running, each stage of the sandbox image (`base`, `bio`, `full`) with whether it is built and about how long it takes, how much of the data lake is there and the space left, the jobs, and a checklist in the order to do it. A conversation whose code runs in Docker is not made while Docker is not running or its image is not built (`setup_needed`), rather than failing when its code first runs; `create_app(check_setup=False)` turns that off.
- `POST /api/setup/images/{stage}` starts building a stage, and `POST /api/setup/data-lake` fetches the data lake (all of it, or `{"names": [...]}`), each answering at once (202) with a job. `GET /api/setup/data-lake` lists its files and which are there. A job reports what it is doing, its progress (the files and bytes fetched), and what it printed, from `GET /api/setup/jobs/{id}?log_from=` so that a page asks only for what is new; `POST /api/setup/jobs/{id}/stop` stops it, ending the build or leaving no part of a file, and stopping the server stops what is running. One image is built at a time, and one fetch runs at a time.
- `GET /api/papers` lists the runs that read papers for what tools and data they use (the [paper reading](papers-and-functions.md#growing-the-toolset-from-papers) of the library), and `POST /api/papers/runs` makes one from `{"title": ..., "source": {...}}`, where the source is `{"kind": "files"}` (papers you upload to it), `{"kind": "folder", "path": ..., "recursive": ...}` (a folder on this machine, by its full path, which is read where it is), or `{"kind": "biorxiv", "since": "YYYY-MM-DD", "until": ..., "subject": ..., "limit": ..., "random": ..., "include_unpublished": ...}`. A source that is sent something that is not for its kind is refused. `GET /api/papers/runs/{id}` shows a run: its papers with whether each is `pending`, `read`, `unavailable`, or `failed`, what has been spent, the files uploaded, and the first rows of what was found (`tasks`, `databases`, `software`); `DELETE` removes it unless it is being read. `POST /api/papers/runs/{id}/files?name=...` uploads a paper as the body (a PDF, or a text, Markdown, or LaTeX file, up to the upload limit, at most 500 to a run) and `DELETE /api/papers/runs/{id}/files/{name}` takes one away; neither is allowed while the run is being read.
- `POST /api/papers/runs/{id}/read` starts reading with `{"max_cost": ..., "max_cost_per_paper": ..., "retry_failed": ...}`, answering at once (202) with a job that is listed with the setup jobs and stopped the same way. How much it may spend is always said, and the model in the settings needs its key and a known price so that the limit can be kept (`missing_keys`, `unavailable`, 422). Papers already read are not read again, so a run that was stopped, or ran out of money, carries on from where it was; a run that was read with another model is not read with this one (`different_model`, 409), and one run is read at a time (`busy`, 409). `GET /api/papers/runs/{id}/tables/{kind}` sends what was found as a CSV file. Runs are kept in `papers/` in the workspace.
- `POST /api/papers/runs/{id}/functions` writes functions for what a run's papers share, as the library's [function writing](papers-and-functions.md#growing-the-toolset-from-papers) does: one for each task found in at least `min_papers` of them (1 unless said), the most common first, up to `limit` (10 unless said, at most 100). It answers at once (202) with a job, and says what it may spend in `max_cost` (always required, as for reading) and, if it likes, `max_cost_per_function`; `retry_failed` writes again those an earlier writing could not make pass, and `verify` also imports each function in a container of the sandbox, which Docker must be running for, before keeping it (`setup_needed`, 409, where it is not). The papers must have been read first, and a run is only ever being read or written for, not both (`busy`, 409). A function already written is not written again, so a run that stopped, for its limit or a request to stop, carries on from where it was. `GET /api/papers/runs/{id}` lists the functions (`functions`: the task, whether it was `verified`, `unverified`, or `failed`, the modules it needs installed, and what it cost), `GET /api/papers/runs/{id}/functions/{name}` shows one with its code, so that it can be read before it is relied on, and `DELETE` takes one away.
- A run's functions are code a model wrote, so a conversation is given them only if the person says: `PATCH /api/papers/runs/{id}` with `{"given": true}` gives them to the conversations that are made from then on (`given` in the run, and `function_count` of those that passed), or `POST /api/chats` names runs in `functions` (a run that has none is refused), which its `config` says. Each function is a tool of the conversation, described by its docstring, that runs where its code does, in the sandbox if that is Docker, and is left out where code runs nowhere. A function whose name is a tool's already is left to that tool, and of two runs with a function of one name the first is given. The web interface's PaperAgents page, in its Surveys part (`/papers?view=surveys`), is where runs are made, read, and given.
- `GET /api/paperagents` lists the [PaperAgents](paperagents.md) (a paper, with the code that came with it, that is to be made usable), the latest first, with `max_agents`, `max_paper_bytes`, `suffixes`, and `repo_hosts`; `POST /api/paperagents` makes one from `{"title": ..., "paper": {"kind": "doi", "doi": ...}, "repo": ...}`, where `paper` is a DOI, a link (`{"kind": "url", "url": ...}`), or a file that is uploaded afterwards (`{"kind": "file"}`), and `title` and `repo` may be left out. `GET`, `PATCH` (`title`, `repo`), and `DELETE /api/paperagents/{id}` show, change, and delete one; `POST /api/paperagents/{id}/paper?name=...` uploads the paper file of an agent, and `DELETE` on the same address takes it away. `POST /api/paperagents/{id}/reading` (with `max_cost`, always given) reads the paper as a job, which first fetches the text of a DOI (from Europe PMC, for the papers that are open access) or of a link (from the public internet only) that has no file, and says why and asks for the file if it cannot, and `GET` and `DELETE` on the same address show and clear what was read: claims, a draft method card, and resources, each with a quote that is word for word in the paper; `GET /api/paperagents/{id}/passage?start=&end=` gives the words at a place in it. `POST /api/paperagents/{id}/repository` fetches the agent's code as a job, at one commit and with none of it run, and takes stock of it (`{"repo": ..., "ref": ..., "max_megabytes": ...}`, all optional), `GET` on the same address gives what was found, whether to go on with it (`preflight`: go, ask, or no-go, with its checks and a cost estimate), and the projects the paper points to for a person to choose from, and `DELETE` takes the code away. `POST /api/paperagents/{id}/environment` builds, as a job, an environment from the code's own files (pip or conda) in a container that has none of this machine in it, with limits on its time (`minutes`) and disk (`gigabytes`) and optional `python` and `system_packages`, and keeps it as an image that is then run with no network; `GET` on the same address gives what would be built, what was, or why a build failed (a classified reason, with its output), `DELETE` takes it and its image away, and `GET` on `/environment/lock` and `/environment/log` give the exact versions and the output. One paper is one agent, so a DOI, a link, or a file that an agent has already is refused with that agent (`exists`, 409, with `existing`). Agents are kept in `paperagents/` in the workspace.
- Everything is kept in the workspace, `~/virtual_lab_workspace` unless `--workspace` says otherwise: `settings.json`, `scientists.json`, `campaigns.json`, `tools.json`, `skills.json`, `mcp.json`, `own.json` and the files you uploaded in `own_data/`, a directory for each conversation in `chats/`, named for the date and the title, and `data_lake/`. They are plain files, so a change made to one by hand is met rather than trusted: a setting in `settings.json` that is not of the kind it is (a budget that is not an amount of money, a switch that is not true or false) takes its default, a setting that is the right kind but cannot be used, such as a model nothing serves, is said to be wrong when a conversation is begun and does not stop another setting from being changed, and a conversation whose `chat.json`, `events.jsonl`, or `messages.jsonl` holds something a conversation does not save is not opened, with the file named, and can still be deleted. Entries of `scientists.json`, `campaigns.json`, `tools.json`, `skills.json`, `mcp.json`, and `own.json` that are not what they should be are left out.
- With `--static-dir` (or pages in the install), the server also shows the built pages of an interface, and any address that is not a file or under `/api` shows its first page.

### The chat interface

The pages that talk to this server are in `web/`, written with Next.js, React, Tailwind, and shadcn/ui, and exported as static files: nothing runs but the server. They start a conversation with the lead scientist (the first page says when the model has no key, and opens the keys to add one), show its reply as it is written, list the conversations on the side, choose the model for a new conversation, or change it in one that is going on once it has finished (useful when a provider stops a conversation for its safety rules, or to try another model on the same question), search every model OpenRouter serves, set the model, the keys, where code runs, the scientists, the tools, and the MCP servers, ask before a call that costs money or cannot be undone and put a server's questions as forms, build the Docker image and fetch Biomni's data lake while showing what each prints, and say when the server cannot be reached or no longer accepts the token. They need Node 22 or later to build, and nothing at all to use once built.

From a clone of this repository, one command does all of that, and starts the server:

```bash
python3 start.py                        # then open the link it prints (it also opens it)
python3 start.py --workspace ~/lab --port 9000 --no-browser
python3 start.py --plan                 # what it would do, without doing it
python3 start.py --rebuild              # build the pages again
```

It needs Python 3.12 or later to run, and Node 22 or later the first time, to build the pages. It makes a Python environment in `.venv` (or uses the one you are in, if you are in one), installs the lab in it with the `server`, `mcp`, `papers`, and `eval` extras, runs `npm ci` and `npm run package` in `web/`, and starts `virtual-lab-server`, giving it whatever else you wrote. Each of those is looked at first and left alone if it is done, so the first start takes a few minutes and the next ones a moment; the pages are built again when something in `web/src` or the files npm reads has changed since they were built, as after a `git pull`. A step that fails stops it, says which, and is tried again the next time. It starts the server from the clone's directory, so a `.env` file there with your keys in it (`OPENAI_API_KEY=...`) is read, and `.env` is not kept in version control. Without Node, it uses pages that are already built and says so, and otherwise says what to install. The same, by hand:

```bash
pip install -e ".[server,mcp,papers,eval]"
cd web
npm install
npm run package                         # the pages, into src/virtual_lab/server/static
virtual-lab-server                      # now shows them at the link it prints (or python -m virtual_lab.server)
```

`npm run package` is what makes a build of the package carry the pages (they are not kept in the repository). To change the interface, build into `web/out` with `npm run build` and run `virtual-lab-server --static-dir web/out`. `npm run lint`, `npm run typecheck`, and `npm test` check the code, and `npm run test:e2e` drives a browser through the built pages against the real server with a script where the model would be, so it needs no key. See `web/README.md`.

The chat interface is the one page. It does not set up a meeting itself: in a conversation the lead brings in the team for a meeting when a question needs it, and a meeting run from a script, with `hold_meeting` or `Project`, is saved and resumed as [described for projects](projects.md#running-a-project-within-one-budget-and-resuming-it).
