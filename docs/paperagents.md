# PaperAgents

[Back to the README](../README.md). A PaperAgent is one paper, with the code that came with it, made into something the lab can use.

This is built one step at a time. So far an agent is the record of what it is to be made from (which paper it is of, and where its code is), its paper can be [read](#reading-the-paper), after its text is [fetched](#fetching-the-paper) if it is a DOI or a link, its [code can be fetched](#fetching-the-code) at one commit, taken stock of, and checked for whether it is worth going on with, an [environment can be built](#building-the-environment) for the code from its own files, in Docker, as an image that is the same each time it is used, [the data](#getting-the-data) that the paper used can be listed, and fetched for the files a person chooses, from a short list of places, and [the tutorials](#running-the-tutorials) of the code can be run in the environment, with what each did kept as the reference run, and [tools can be made](#making-tools) from the calls that the tutorials made, each called again to see that it gives what the tutorial got, and the paper's [claims can be tried](#trying-the-claims) against what the tutorials gave. An agent can be [given to conversations](#using-an-agent-in-a-conversation), which are then given tools that read what was found in its paper and tools that run the authors' code, or, for a paper with none, the function written from it once it matched a number of the paper, labelled as a re-implementation, each with its tier, and each step says `pending` until it is done. An agent that someone else made, such as a server that Paper2Agent hosts, can be [imported](#importing-an-agent-that-someone-else-made), and is then shown as imported and not checked. Reading many papers at once, for the tasks, databases, and software they share, is a different thing, the [surveys](papers-and-functions.md#growing-the-toolset-from-papers), and is still there as the other part of the same page.

## Making an agent

The web interface's PaperAgents page (`/papers`) lists the agents, the latest first, and makes one. An agent is of one paper, given in one of three ways:

- **A DOI**, such as `10.1038/s41586-020-2649-2`. `doi:10.…` and a `https://doi.org/10.…` link are accepted, and the DOI is kept in lower case.
- **A link** to the paper on the web, which begins with `http://` or `https://`. A link to `doi.org` is kept as the DOI it holds. The host is kept in lower case, and a fragment, a closing slash, and the port that the scheme has by itself (80 for http, 443 for https) are dropped. A link to this machine or to a private network is refused (422 `invalid`, saying to upload the paper's file in place of a link): an address that is not on the public internet (loopback, private, link-local, and the like), a name with no dot in it such as `localhost` or `intranet`, and a name ending `.local`, `.localhost`, `.localdomain`, `.internal`, `.intranet`, `.lan`, or `.home.arpa`. A name that leads to such an address only through the DNS cannot be told here, and is refused when the page is fetched.
- **A file** that is uploaded to the agent after it is made: a PDF, or a text, Markdown, or LaTeX file, up to the upload limit (at most 100,000,000 bytes, which the page says as 95 MB). It is kept with the agent, and may be uploaded again to replace it, or taken away.

An agent of a DOI or a link has a file too, beside the DOI or the link, since the text that is read is the file's. It is uploaded, or, if there is none when the paper is read, [fetched](#fetching-the-paper) and kept as the file.

An agent may also say where its code is: the address of a project at github.com, gitlab.com, bitbucket.org, or codeberg.org, such as `https://github.com/owner/name`. A longer address, to a branch or a file, is cut down to the project. Nothing is fetched from it until it is [asked for](#fetching-the-code).

An agent is called by its title. For a DOI or a link the title may be left out, and the DOI, or where the link leads, is used. For a file it is needed, since there is nothing else to call it by.

One paper is one agent. A DOI or a link that an agent has already, or a file with the contents of one an agent has (which is told by its SHA-256, whatever the other agent was made from), is refused with the agent that has it (`exists`, 409), and the page links to it. At most 200 agents can be kept. Two links are one paper only if they are the same once written as above, so `http` and `https` addresses, or the same query in another order, are two links.

An agent's page (`/papers?agent=...`) shows its paper (a DOI or a link opens in a new tab), its code, and how far each step has got. It says again what the agent is called and where its code is, uploads or removes the paper file (for an agent of a DOI or a link too, which shows where a fetched file came from), and deletes the agent, after asking, with the paper that was uploaded to it. Its Reading part asks for the most the reading may spend and reads the paper (fetching it first if it is a DOI or a link with no file), follows the job and can stop it, and shows what was found: each claim, piece of software, link, license, and statement of where the data and code are, with the paper's words for it, and the paper at that place on asking. It can read again the parts that failed, and clear the reading, after asking (what a person did to the method card is kept). Its Method card part shows the draft of what the method was done with and tested on, with each fact marked as read by the model or as the person's, says whether it is a draft, approved, or approved and changed since, and lets a person change, add, take off, and put back facts, approve the card, take the approval back, and discard all that they did (see [The method card](#the-method-card)). Under what the method was tested on it has a form, Check my data against the card, where a person says what their data is (species, tissue, assay, input format, and a sample size with what it counts) and is shown whether it is inside, outside, or not covered, with a warning that quotes the card and the paper for each thing that is outside, what the card says of each, and how far the card and the reading are to be trusted; the answer is gone when the card changes (see [The method card](#the-method-card), under Checking data against the card). Its Code part lists the projects the paper points to, for a person to say which is the code (asking first if that takes away code that was fetched), fetches the code at a branch, a tag, or a commit with a limit on how much, follows the job and can stop it, and shows the commit, what was found in the files, and whether it is worth going on with, each check with how it came out in words; the code can be taken away, after asking. Its Environment part, once the code is fetched, shows what would be built (how, from which files, with which Python, starting from which image, and the steps), asks for a Python, Debian packages to install first, and the most time and disk, and says what is wrong with them before anything is sent. It follows the build as it prints, and can stop it, and nothing else is done to the agent while it goes on. Then it shows what was built (the Python, the number of packages, the image's hash, its size, what `pip check` said, each step with its time), the exact versions and what the build printed when they are asked for, and that all that is known is that it starts, and takes the environment away, after asking. A build that failed shows the likeliest reason, the end of the step's output, and a button that fills the form in with what it suggests (it does not send the form). A project that is not built here says why, and Docker not running is said, with the form switched off. Its Data part shows the datasets the paper names, each with the paper's words for it and the place its accession is of, and the places that the paper and its code name for the data; a place that is not fetched from here is shown with why. A person looks at what a place has (or types an address, a DOI, or an accession), which asks that place and fetches nothing, chooses files from the list (each with its size, how it will be checked, and what the place says if it cannot be fetched), says the most to fetch, and is told in words what it comes to, which hosts are asked, and how many files are checked by a checksum and how many by their size only, before agreeing. The job is followed as it prints, with the files and bytes done, and can be stopped; nothing else is done to the agent, and its paper is not read, while it goes on. What was fetched is shown by place, with each file's size, how far it was checked (the checksum of the place, or its size only), and the start of its SHA-256, and a place's files, or all of them, are taken away after asking. Beside each dataset, a person says which of their own data stands in for it, or takes that away; one that the paper does not name can be named by hand. Its Tutorials part, once the environment is built, lists the tutorials that would be run and those that cannot be, with why, asks for the most time for one and for all, how many, how many times each, and the most one may write, and whether the runs are given the data that was fetched, and says what is wrong with them before anything is sent. It follows the run as it prints, and can stop it, and nothing else is done to the agent while it goes on. Then it shows how each tutorial ended and whether its runs agreed, in words, which were not run, and what the run was given and allowed; what one did (the calls it made, the files it wrote, what it printed, and why it failed) is looked at when it is asked for; and what was kept is taken away, after asking. Its Tools part, once the tutorials have been run to their end, shows which of the functions they called would be made into tools and which would not, with why, asks for the most time for the calls of one tool and for all of the tools, how many tools, how many times each call is made again, how many times a wrapper may be rewritten, and the most one call may write, and says what is wrong with them before anything is sent. It follows the making as it prints, and can stop it, and nothing else is done to the agent while it goes on. Then it shows each tool made (its tier, how many of the tutorials' calls were made again, and that each gave what the tutorial got), the functions that were not made, with why and what was found, and what was allowed; a tool's wrapper and the evidence for it (each call, what it was given, what the tutorial got, and what it gave) are looked at when they are asked for; and the tools are taken away, after asking.

## What is kept

Each agent is a directory of its own in `paperagents/` in the workspace, named from its title:

```
paperagents/<id>/
    agent.json         schema, title, created_at, paper, repo, steps, given if the person said so, and imported if it was
    paper/             the paper file (uploaded, or fetched), and once it is read, text.txt and layout.json
    claims.json        what the authors report, each with its quote and where it is
    method_card.json   a draft of what the method was tested on and where it falls short
    method_card_edits.json
                       what a person did to the card: the facts they changed or added, those they took off, and their approval
    resources.json     the software, links, statements of where data and code are, and licenses
    log/reading/       run.json, and chunks/NNNNN.json, one for each chunk that was read
    repo/              the project's files at the commit that was fetched, read only, once it is fetched
    intake.json        where the code came from, which commit, when, the limit, and what was found in it
    env/               environment.json (what was built, from which commit, and the image's hash), the lock, and build.log;
                       failure.json instead of the first if the last build failed
    data/              the files that were fetched, in <place>/<id>/, as the place names them
    data.json          where each file came from, its size and checksums, and which of the person's own data stands in for what
    checks/            reference.json (the account of running the tutorials, of one commit and one image), and in reference/<tutorial>/,
                       detail.json (what that tutorial did) and files/ (what it wrote, if small);
                       tools.json (the account of making the tools: which were made, which were not and why)
    tools/<name>/      wrapper.py (the tool: it calls the paper's own function and does nothing else), and tool.json (its
                       signature, its tier, and each call that was made again, with what it gave)
    checks/independent/<tool>/<kind>.json
                       one check of one tool, by what its tutorial did not give it: whether it passed, failed, or was not
                       obtained, what it came to, what it was made of, and the hash of the wrapper, the commit, the image,
                       and the reference run it is bound to
    checks/reproduction.json
                       the account of trying the paper's claims against what the tutorials gave: for each claim, whether it was
                       reproduced, partly, not, or not attempted, and why, and against what, bound to the commit, the image,
                       the reference run, and the claims it was made of
    checks/variants.json
                       the variants that a person asked for of those claims (a claim's call made again with arguments changed),
                       each with what was changed and what came of it, bound to the same, and to the trying of the claims;
                       never part of reproduction.json
```

`agent.json` is written all at once, so that it is never half written, and says which version of the record it is (`schema`), so that a later version can read what an earlier one wrote. `given` is `true` only if the person said so, and anything else in its place is the same as it being left out. `imported` is there only for an agent that was imported (see below), and is the server's `kind`, `url`, `origin`, `imported_at`, `checked_at`, and `tools`; one that was edited into something that is not fit makes the directory not an agent. A directory without a valid `agent.json` is not an agent and is not listed, nor is one whose file was edited to hold a DOI, a link, or an address of code that would not be taken when it is given, nor is a directory that is a link to another. `repo/` is only there with an `intake.json` that is fit and is of the address the agent has now, and one that was edited into something that is not, or that is of another address, is not taken for the agent's code. `env/` is only shown when its record is fit, is of the commit that the code has now, and has its lock beside it. `checks/reference.json` is only shown when it is fit, and is of the commit that the code has now and the image that the environment is, and only the tutorials whose `detail.json` is there are listed; a tutorial's folder that is a link is not followed. `checks/tools.json` is only shown when it is fit, and is of the commit, the image, and the reference run that are kept now, and only the tools whose files are there are listed; a tool is only read back if its record is fit, its `wrapper.py` is what was hashed when it was made, and that still passes the check that it calls the paper's function and does nothing else, so a wrapper that was edited is not a tool, and a tool's folder that is a link is not followed. A check in `checks/independent/` is only counted when it is fit, is of that tool and kind, and is bound to the wrapper's hash, the commit, the image, and the reference run that are kept now (and, if it is against the paper's numbers, to a hash of the numbers that `claims.json` holds now); one that is bound to something else is shown as stale and counts for nothing, and one that is a link, too big, or not fit is shown as not made. They go with the tools. The image itself is in Docker, named `virtual-lab-paperagent:<id>-<first 12 of the commit>`, and is looked for by that name, never by a name in a file. `data.json` says only what is true of what is in `data/`: a path that is not where the place and the name would put a file, a checksum that is not one, or a place that is not one of those that data is fetched from is left out when it is read, so a record that was edited cannot point outside `data/`. Later steps will keep what they make in directories beside these. The paper's text goes to the model that reads it, and nowhere else.

## The API

All of it needs the server's token, like the rest of the API.

| Request | What it does |
| --- | --- |
| `GET /api/paperagents` | The agents, the latest first, and what a page needs to make one: `max_agents`, `max_paper_bytes`, `suffixes`, and `repo_hosts`, and `importable`, the servers that others host which can be imported, each with its `key`, `title`, `about`, `made_by`, `url`, `site`, `paper`, `repo`, the `agent` that has it already (or `null`), and the `paper_agent` that is of its paper (or `null`). |
| `POST /api/paperagents` | Makes an agent from `{"title": ..., "paper": {...}, "repo": ...}`, where `paper` is `{"kind": "doi", "doi": ...}`, `{"kind": "url", "url": ...}`, or `{"kind": "file"}`, and `title` and `repo` may be left out as above. Answers 201 with the agent. |
| `GET /api/paperagents/{id}` | One agent: `id`, `title`, `created_at`, `paper`, `repo` (or `null`), `given`, `imported` (or `null`, see below), and `steps`, which says `pending`, `running`, `done`, `failed`, or `skipped` for each of `reading`, `repository`, `environment`, `data`, and `tools`. |
| `PATCH /api/paperagents/{id}` | Says again `title`, `repo`, and `given` (`true` or `false`, and nothing else), at least one of them. What is left out is left as it was, and an empty `repo` takes the code away. `given` says whether conversations that are made from then on are given the agent. |
| `DELETE /api/paperagents/{id}` | Deletes the agent and its paper, and answers with the list. While Docker takes its image away, which can take a while when Docker is slow, the agent is gone to everything else (404 on every address of it, and not listed), and other agents are not held up; if the image cannot be taken away (409 `docker`) the agent is there again as it was. |
| `POST /api/paperagents/{id}/paper?name=...` | Gives an agent its paper file, as the body, in place of one it had, and takes away what was read of the one before. Answers 201 with the agent, as the upload of a paper to a survey does. A file that is not a paper, or is over the limit, is refused (422, 413). |
| `DELETE /api/paperagents/{id}/paper` | Takes the uploaded paper away, and what was read of it. |
| `POST /api/paperagents/{id}/reading` | Starts reading the paper, from `{"max_cost": ..., "retry_failed": false}`. The limit on spending, in dollars, is always given. Answers 202 with the job, which the setup jobs routes (`/api/setup/jobs/{id}`, and `/stop`) follow. A DOI or a link with no file is fetched first, by the same job. |
| `GET /api/paperagents/{id}/reading` | What has been read: `has_paper` (there is a file), `has_text`, `fetchable` (the paper is a DOI or a link with no file, so reading it fetches it), `source` (where the file was fetched from, or `null`), `chunks`, `read`, `skipped`, `failed`, `complete` (every chunk has come to something, which a reading that stopped at its limit has not), `dropped`, `cost`, `calls`, `models`, `truncated_from`, `finished_at`, the running `job` if there is one, and the `claims`, the `card` (the draft with a person's edits put over it, see [The method card](#the-method-card)), and the `resources`. |
| `DELETE /api/paperagents/{id}/reading` | Takes away what was read, so that the paper can be read again from the start. The paper stays, and so does what a person did to the card. |
| `POST /api/paperagents/{id}/card/facts` | Adds a fact to the method card, which is the person's own, from `{"kind": "methods" \| "datasets" \| "scope" \| "limitations", "fields": {...}}`: the fields are those of the kind (`name`; `name` and `accession`; `aspect` and `value`; none for a limit), and `quote`, the fact's own words, which a limit must have. Answers with the reading, as `GET .../reading` gives it. |
| `PUT /api/paperagents/{id}/card/facts/{fact}` | Changes a fact of the card to say what `{"fields": {...}}` says, all of its fields. The fact is then the person's, keeps the paper's words and where they are, and says what it was read as. A fact that a person added may have its `quote` changed too. A limit that was read is not changed (take it off and add one). Changed back to what it was read as, it is the reading's again. |
| `DELETE /api/paperagents/{id}/card/facts/{fact}` | Takes a fact off the card. One that a person added is gone; one that was read is kept aside, in `card.removed`, and can be put back. |
| `POST /api/paperagents/{id}/card/facts/{fact}/restore` | Puts back a fact that was taken off, or has a fact that a person changed say what it was read as. If the reading no longer finds the fact there is nothing to put back (422). |
| `POST /api/paperagents/{id}/card/approval` | Approves the card as it is now. A card with no fact on it is 422, and one whose paper is being read 409 `busy`. |
| `DELETE /api/paperagents/{id}/card/approval` | Takes the approval back. |
| `DELETE /api/paperagents/{id}/card/edits` | Takes away all that a person did to the card, and the approval, so that it is as it was read. |
| `POST /api/paperagents/{id}/scope-check` | Puts what a person's data is against what the card says the method was used on, from `{"species": ..., "tissue": ..., "assay": ..., "input_format": ..., "sample_size": ..., "sample_unit": ...}`, any of which may be left out, though at least one must be said (a size is a whole number from 1, and `sample_unit` is what it counts, which needs a size). Answers `outcome` (`outside` if the data is outside in anything, `inside` if it is inside in everything that was said of it, otherwise `not covered`), `aspects` (for each thing said: what was `given`, its `outcome`, the card's statements it was put against as `says`, each with `value`, `quote`, `by`, `changed`, `page`, and `section`, and the `reason`), `warnings` (one for each thing that is outside, with the card's words), `not_checked` (what the card says of what nothing was said of), `card` (`status`, `approved_at`, `changed_since_approval`, `edited`, `scope_facts`), `reading` (how far the paper was read), and `notes`. It changes nothing and refuses nothing because the data is outside. |
| `POST /api/paperagents/{id}/repository` | Starts fetching the code, from `{"repo": ..., "ref": ..., "max_megabytes": ...}`, all of which may be left out: `repo` is the address to fetch, which is kept as the agent's in place of what it had (left out, the agent's own is fetched), `ref` a branch, a tag, or a commit (left out, the project's default branch), and `max_megabytes` the most to fetch, from 10 to 1,000 (left out, 200). Answers 202 with the job. Without an address it is 422 `no_repo`, without Git on this machine 422 `git_missing`, and for code that has been fetched already 409 `done`. |
| `GET /api/paperagents/{id}/repository` | What there is of the code: `repo` (the agent's, with `ref` and `commit` once fetched), `cloned`, `intake` (`url`, `ref`, `commit`, `cloned_at`, `limit_bytes`), `stock` (what was found in it), `preflight` (whether to go on: `verdict`, `summary`, `checks`, `estimate`), `candidates` (the projects the paper points to, to choose from), the running `job`, `git` (whether Git is installed), and `limits`. `stock` and `preflight` are `null` until the code is fetched. |
| `DELETE /api/paperagents/{id}/repository` | Takes away the code that was fetched, and what was found in it, so that it can be fetched again. The address stays. |
| `POST /api/paperagents/{id}/environment` | Starts building the environment, from `{"python": ..., "system_packages": [...], "minutes": ..., "gigabytes": ...}`, all of which may be left out: `python` is a version to build for in place of what the code says, `system_packages` are Debian packages to install first, and `minutes` (1 to 180, left out 30) and `gigabytes` (1 to 40, left out 6) are the most time and disk the build may take. Answers 202 with the job. Docker not running is 422 `docker_missing`, no code fetched 422 `no_code`, a project that is not built here 422 `unsupported` (with `reason`: `no_environment`, `r`, `julia`, `docker`, `pipfile`, or `python_mismatch`), and an environment that is built already 409 `done`. |
| `GET /api/paperagents/{id}/environment` | What there is of the environment: `docker` (`ready`, and `message` if not), `commit` (of the code), `recipe` (what would be built and how, for the `python` and the repeated `system_packages` in the query if they are given, which builds nothing), `unsupported` (`kind` and `message`, instead of the recipe), `built` (the record, with `image_present`, which says whether the image is still in Docker, or `null` if Docker cannot be asked), `failure` (why the last build failed), `has_log`, the running `job`, `limits`, `python_versions`, and `max_system_packages`. |
| `DELETE /api/paperagents/{id}/environment` | Takes away the environment and its image, and what was kept of a build that failed, so that it can be built again. If Docker cannot remove the image it is 409 `docker`, and nothing is taken away. |
| `GET /api/paperagents/{id}/environment/lock` | The exact versions that were installed, as `{"name": ..., "text": ...}`. |
| `GET /api/paperagents/{id}/environment/log` | What the last build printed, as `{"lines": [...]}`, whether it worked or not. |
| `POST /api/paperagents/{id}/reference` | Starts running the code's tutorials in the environment, from `{"minutes": ..., "total_minutes": ..., "tutorials": ..., "repeats": ..., "gigabytes": ..., "data": ...}`, all of which may be left out: `minutes` (1 to 60, left out 10) is the most time one run of one tutorial may take, `total_minutes` (1 to 240, left out 30) the most for all of the runs, `tutorials` (1 to 25, left out 10) how many are run, `repeats` (1 to 3, left out 2) how many times each is run, `gigabytes` (1 to 20, left out 2) the most one run may write, and `data` (left out, yes) whether the runs are given the data that was fetched, to read. Answers 202 with the job. Docker not running is 422 `docker_missing`, no code 422 `no_code`, no environment 422 `no_environment`, an image that is not in Docker 409 `image_missing`, no tutorial in Python 422 `no_tutorials`, and tutorials that have been run 409 `done`. A run that was stopped or failed is not `done`, and is replaced by the next. |
| `GET /api/paperagents/{id}/reference` | What there is of it: `docker`, `commit`, `environment` (`built`, and `image_present`), `plan` (the `runnable` tutorials, each with the `id` it is kept under, its `path`, and its `kind`; those that are `skipped`, each with `path`, `kind`, and `reason`; and how many `more` there are than were listed), `data` (`files` and `bytes` that a run would be given, or `null`), `kept` (the account of the last run: `commit`, `image_id`, `started_at`, `finished_at`, `complete`, the `limits` and `data` it had, a summary of each of its `tutorials`, those `skipped`, and those `not_run` with why, or `null`), the running `job`, `meaning` (what a reference run is, in words), and `limits`. |
| `GET /api/paperagents/{id}/reference/{tutorial}` | What was kept of one tutorial: `status` (`ok`, `failed`, `timed_out`, or `too_big`), `failure` (`kind`, `title`, `detail`, and the `tail` of what it said), `python`, `seconds`, `runs` (how each run ended, with `digest`s of what it did), `stable`, `differs`, `output` (the end of what it printed), `cells` (for a notebook: each cell's output, and what it skipped), `calls` (the project's functions it called, with the arguments and the result of each), `calls_seen`, `files` (each written: `path`, `bytes`, `sha256`, `new`, and whether its content is `kept`), `files_more`, and `packages` (the project's packages that were imported). A tutorial that is not in the account is 404. |
| `DELETE /api/paperagents/{id}/reference` | Takes away what the tutorials gave, with the files kept, so that they can be run again. The tools that were made from it go too. |
| `POST /api/paperagents/{id}/tools` | Starts making tools from the calls that the tutorials made, from `{"minutes": ..., "total_minutes": ..., "tools": ..., "repeats": ..., "repairs": ..., "gigabytes": ...}`, all of which may be left out: `minutes` (1 to 30, left out 5) is the most time that all of the calls of one tool may take, `total_minutes` (1 to 120, left out 20) the most for all of the tools, `tools` (1 to 50, left out 20) how many are made, `repeats` (1 to 3, left out 2) how many times each call is made again, `repairs` (0 to 3, left out 2) how many times a wrapper that does not pass the checks of one is rewritten, and `gigabytes` (1 to 20, left out 2) the most that one call may write. Answers 202 with the job. ## Reading the paper

Reading turns a paper's text into facts that its own words bear out. It is a job, so that it can be followed and stopped, and it needs the paper's file (or a DOI or a link to [fetch](#fetching-the-paper) it from), a model with a key and a known price (the model in the settings), and a limit on spending, which is always given and is never exceeded by more than the one request that was in flight.

**The text.** The file's text is read, a page at a time for a PDF, and kept in `paper/text.txt` as it is (with plain line ends), with `paper/layout.json` saying where each page and each section begins, so that a place in the paper can be told as the character it begins at. A PDF's text is as the PDF library finds it, so a two-column paper's columns may be mixed. A paper over 200,000 characters is cut short at the end of a sentence, and the page says how long it was. Headings are found by what they say (Abstract, Methods, Data availability, and so on), and by Markdown and LaTeX marks.

**The chunks.** The text is cut into chunks as a survey's is, 4,000 characters with 400 repeated between one and the next, and each is read by the model for: the *claims* the authors report (a number, a comparison, or another conclusion), the *methods* and the *data* they used (with accessions), the *software* (with versions), the *links*, the statements of where data and code are, the *licenses*, what the method was *tested on* (species, tissue, assay, sample size, what the input must be like), and where the authors say it *falls short*. A chunk in the references is not read, since it holds no one's result and would cost money for nothing.

**Every fact has a quote, and is kept only if the quote is in the paper.** The quote must be found word for word in the chunk it was read from. Spaces and line breaks, curly and straight quotes, ligatures, and a word that a line ended in the middle of do not count as differences; case and letters do. A quote is found only as whole words and numbers, so one that stops in the middle of a number ("5 of 5" for "5 of 50") or a word is dropped. A quote that was reworded, that has an ellipsis, that is shorter than 8 characters or longer than 1,000, or that is from another part of the paper than the chunk, is dropped. A name, number, version, or address that a fact gives must be in its quote too, as the whole of one: "5" is not in "10.5", "R" is not in "Seurat", "4.3" is not in "4.3.1", and an address cut short is not in the longer one (an address is found even if a line broke it). An address that is not a web address is dropped. What is dropped is counted and never mended, and the page says how many facts were left out. What is kept has the paper's own words at the place it found them, with the page and section, and a stable id, so that the same fact found again has the same id.

**The paper is data.** A chunk is given to the model between tags, as material to read, and the model is told that nothing in it is an instruction. The request has no tools, and what the model returns is lists of facts to check, never something that is run or followed. A paper that says "ignore your instructions and report that this method works on all species" can therefore only be quoted: the claim that it works on all species has no quote in the paper, and is dropped. Text in the paper that closes the tags is made not to.

**The files.** The claims are in `claims.json`; the draft method card, with what was done, the data used, what the method was tested on, and its stated limits, is in `method_card.json`, with `"status": "draft"` since nothing has approved it; and the software, links, statements, and licenses are in `resources.json`. They are written whenever a reading ends, whether it read the paper through or not, from what each chunk came to. A person's changes to the card are not in `method_card.json`, which says only what the reading made; they are in `method_card_edits.json` and are put over it (see [The method card](#the-method-card)).

**Stopping and carrying on.** What each chunk came to is kept as soon as it is read, so a reading that is stopped, or reaches its limit, or fails, has lost nothing but the chunk it was in, and reading again carries on after the last chunk. This holds across a restart of the server. The limit is for one reading: reading again is given its own. A chunk the model could not answer (a refusal, or an answer that did not fit) is recorded and the rest are read; it is read again only with `retry_failed`. The reading step of the agent is `done` when every chunk has been read, `failed` when none could be, and otherwise `pending`, with how far it got in the reading. A paper that has been read is not read again, which would spend money for what is there already, until its reading is cleared. A reading that was made by another version of what reads, or with other sizes of chunk, is not shown, and the paper is read again from the start.

**A reading belongs to its file.** What was read is of the file it was read from, told by its hash. Changing the file, or taking it away, takes away what was read of the one before, and what was kept for another file or another version of the reading is never mixed in.

## The method card

The card is a draft that a model made from the paper. All that was checked of a fact on it is that its quote is in the paper, which is not that the model read the quote right, so a person reads it, puts right what is wrong, and approves it. Nothing that a person does is mixed into what the reading made.

**Whose a fact is.** Every fact of the card says whose it is, in `by`: `reading` for what the model read, and `person` for what a person changed or added. A fact that a person changed keeps the paper's words and where they are, since those are the evidence, and says what it was read as (`read_as`); the paper's words are never changed. A fact that a person added has their own words, if they gave any, in `quote`, and no place in the paper (`anchor` is `null`). A fact that a person took off is not on the card, and is listed in `card.removed` so that it can be put back. A person may change what a method or a dataset is called, its accession, and what a statement of scope is about and says (`aspect` is one of `species`, `tissue`, `assay`, `sample size`, `input`, `other`); the card never holds the same fact twice, and a person may have at most 200 facts of their own. These are in `method_card_edits.json`, with the hash of the file they were made for, and are put over the reading each time the card is asked for.

**Approval.** Approving says that a person read the card as it is and let it stand, with when. It is not that the card is right. It is of the card as it was: if a person changes it, or a reading finds something else, the card is a draft again (`status` is `draft`, `changed_since_approval` is `true`, and `approved_at` is `null`), so an approval never covers what the person did not see. Putting the change back makes it the card that was approved again. A card is not approved while the paper is being read, since it is still being made, and one with no fact on it is not approved, since there is nothing to say.

**What stays when the paper is read again.** What a person did is kept when the reading is cleared, and is put over the next reading: a fact is told by its id, which is the same when the same fact is found again, and what a person changed of a fact that the reading no longer finds stays on the card as theirs. An approval holds for a card that comes out the same. Changing the paper, or taking it away, takes away what a person did to the card of the one before, since it was done to that paper's card.

**What the data part and the checks make of it.** The datasets of the card, as a person has put them, are the datasets that the data part lists (`GET /api/paperagents/{id}/data`, each with `by`, and `anchor` that is `null` for one a person added). A dataset that a person added, or whose accession they changed, still points to its place, but no place in the paper is said to give it, since its words are not of what the person put, and the check of whether the data can be found does not count its accession as one in the paper.

**What a conversation is told.** `show_method_card` gives the card with `by` on each fact and says in its notes whether it is approved (as what a person did, and not that it is right), a draft that nobody has approved, or a draft that was approved and has changed since, and which facts are a person's.

**Checking data against the card.** The statements of scope on the card (species, tissue, assay, sample size, input) say what the authors used the method on. Before a tool is run on a person's own data, what that data is can be put against them, as a person says it on the page or as the lead says it in a conversation (`check_scope`, or `POST /api/paperagents/{id}/scope-check`). A program does the comparing and a model does not: it puts the names that mean one thing as one (mouse and *Mus musculus*, scRNA-seq and single-cell RNA sequencing, h5ad and AnnData), and compares a sample size with the range that a statement gives ("at least 500 nuclei", "1,000 to 10,000 cells"). Each thing that is said of the data is then:

- *inside* if the statements of that sort, taken together, name every word of it that says what it is, or give a range that has the size. Data of two things is inside a card that has a statement of each, and "mouse or rat" is not inside a card that says "mouse".
- *outside* if the card has statements of that sort that can be compared and none covers it. This is warned of, with what the card says and the paper's words for it, and where the card's statement is a person's, whose it is and the words they gave. Nothing is stopped: it is a warning that comes before the run, and the person decides.
- *not covered* if the card says nothing of that sort, or says it in words that a program cannot compare: it says what the method was *not* used on (and what that names is not called inside even where another statement says the method is of any), it gives one size and not a range (which covers only that size), or two sizes that are listed and not a range ("10 and 20 donors"; "between 10 and 20" is a range), or it counts something other than what the data does (nuclei and not cells) or counts something where the data's size is given without saying what it counts. It is not called inside, and it is not warned of as outside, since neither is known. What the card does say is shown, so that the person can judge.

The whole is outside if anything is, and inside only if everything that was said is. The check is against the card as a person has put it: a fact they changed is what they say it is, with the paper's words beside it, a fact they added is marked as theirs, and a fact they took off is not there. It errs toward the warning. Inside says that the card says the method was used on data like this, which is not that the method works on it, and outside says that the card does not say so, which is not that it fails: the card is a draft that a model made, unless a person approved it, and it says what the paper tested. The answer says all of that, and how far the paper was read.

**Holding a run on data that is outside.** The check itself changes nothing and refuses nothing. In a conversation, what the lead said the data is when it called `check_scope` is kept, for that conversation and that agent, and each time one of the agent's tools that run is called, it is put against the card as the card is then (so a change the person made since is what it is put against), and the run goes one of these ways:

- *Not put against the card* (the lead never called `check_scope`, or what it said could not be taken): the tool runs, and its result carries `scope: {"checked": false, ...}` and a note that says so and how to do it. The lead is told to call `check_scope` first, and it is not made to, so a run that was not checked says that it was not.
- *Inside, or not covered*: the tool runs, and `scope` says `checked`, the `outcome`, what each thing that was said came to (`of`: the `aspect`, what was `given`, its `outcome`), the card's `status`, the `warnings` if there are any, and a note that inside is not that the tool works on the data and outside is not that it fails. No one is asked.
- *Outside*: the run is held, and the person is asked, in the conversation, with the card's words and the paper's, and what the tool is to be called with, whether to go on. A warning does not stop them: they can always go on. If they do, the tool runs and `scope` says so, `person_went_on: true` and `went_on_at`, with what the data was outside of. If they do not, or no one could be asked (the turn was stopped or the conversation closed before they answered, nothing was answered within an hour, or the tools are used where nothing asks), the tool is not run and the lead is told that the person chose not to go on, or why they could not be asked, and not to ask again for the same data. Only the person's answer is a go-on: the lead has no argument to say it with, and is told that nothing it says or finds is to be taken for it.

The person is asked once for the same data against the same words on the card, so a second tool of the agent run on it is not asked about again and its result says when they went on (a go-on is for the agent's tools on that data, and the question says so); if what the lead says the data is changes, or the card's words for it do, they are asked again, and that includes while they are being asked: once they have answered, the data and the card are looked at again, and the tool is run only on what they went on with. Calls made at once are asked about once. If the data or the card keeps changing so that it takes more than three questions, the tool is not run and the lead is told. There is still a short time between the card being looked at and the tool starting, in which a change to the card is not seen. The question is the same as a call that waits for approval, an `approval` event with `about: "scope"` and the `warnings`, and it is answered the same way (`POST /api/chats/{id}/approvals/{request}`).

## Fetching the paper

A paper that is a DOI or a link has no file until one is uploaded or fetched. When it is read and has none, the first part of the job gets its text ("Fetching the paper"), which costs nothing and is not held to the limit on spending, and then reads it as any file is read. A request to stop is met when the fetching ends, and keeps nothing.

**A DOI is looked up in Europe PMC**, which holds the full text of the papers that are open access, and nowhere else. A paper that is not open access, or that Europe PMC holds only as an abstract, is not got round: the job fails and says which it is and asks for the paper's file. So does a DOI that Europe PMC does not have, or that it answers with another article's, or a Europe PMC that cannot be reached (which says to try again). The text is the article's abstract, its body, and the sections after its body that say where the data and the code are and what the supplementary material is, each under its heading, marked as Markdown marks one. The references, and what thanks people, says who paid, declares competing interests, says who did what, or gives the authors' details, and the abbreviations, are left out, since nothing in them is a result and they would cost money to read.

**A link is read as a page is read for a model**: HTML as text with its headings, and a PDF as its text. It is refused if it does not lead to the public internet, which is checked when its name is looked up, at every redirect, and at the connection that is made, so that a name that leads to a private address, or is changed to one after it was looked up, reads nothing. An address with a port other than the standard one, with a name and password in it, or that is not http or https, is refused too. The page is not asked to run scripts, so one that is made by them has no text.

**Too little text is refused.** A text of fewer than 3,000 characters is not a paper, and is most likely an abstract, a login, or a payment page, so the job fails and says so rather than read it for money. One of more than the upload limit is refused too.

**What is kept.** The text is kept as the paper's file, `paper/europepmc-<pmcid>.txt` or `paper/linked-paper.txt`, and the file's record in `agent.json` says where it came from: `source` is `{"kind": "europepmc" or "link", "label": ..., "url": ...}`, which the page shows with a link there. The address is where the page ended up after its redirects; if that is longer than an address is kept as, or is not one, the address that was asked for is kept in its place, so that a site cannot make the agent unreadable by sending a link on to one. From then on it is a file like any other: its hash is what a reading belongs to, it is not fetched again to read the paper again, another agent that has the same text is refused as for an upload (the job fails and says which agent has it), uploading a file replaces it and takes the source away, and taking it away leaves the DOI or the link to be fetched again. The step of reading is `failed` when a paper could not be fetched, and `pending` when the fetching was stopped; reading again asks again.

**The paper is data here too.** What is fetched is read as text and given to the model between tags as any paper is. A page that says what to do is only quoted.

## Fetching the code

The code of a paper is fetched as a job (`paperagent-repository`), which can be followed and stopped, from the address the agent has. The paper does not have to have been read, but if it has, what it says is used.

**The paper points to it; a person says which.** Once the paper has been read, `candidates` lists the projects that its links lead to at github.com, gitlab.com, bitbucket.org, and codeberg.org, each once, with the paper's words that give it and whether the paper said it was of the code, those that it did first. A link that is to a page of the host that looks like a project (`github.com/orgs/…`, `/sponsors/…`, `/features/…`, and the like) is not one, and nor is a link to data or to any other host. Nothing is fetched until it is asked for, and fetching one of them makes it the agent's code, in place of what the agent had. If it was different, what had been fetched from the old address is taken away.

**One commit, pinned.** Git fetches the one commit that `ref` names, with none of its history, and the files are written out. The commit, all of its 40 characters, is kept with `ref` in the agent's `repo`, and in `intake.json`, so that it is the same code when it is used again, whatever the project does later. A `ref` that could be taken for an option or a path (a dash first, `..`, a space) is refused (422 `invalid`).

**Nothing in it is run.** Git is run with none of the person's settings, in a home with nothing in it, with no hook, no filter (so Git LFS does not run), no credential helper or prompt, and only https. Submodules are not fetched, and files that the project keeps in LFS are left as the pointers they are, which are noticed. A symbolic link is written as a file that holds where it points, so that nothing in the project reaches out of its folder. Git's own files are taken away. The files are then made read only. Looking at them afterwards is done by reading them, and no part of the project is imported, built, or run. Running it is left to a later step, which will do it in a container and not on this machine.

**There is a limit on size.** What is fetched is watched while Git works, since the size of a project is not known before: the limit is for what is fetched, and again for the files that are written out. A project over it is refused (the job fails), and says how far it got: "The code is more than 200.0 MB, which is the most that is fetched. It had come to 214.3 MB." Before any file is written, Git's list of the commit's files is read, and a project whose files would take more than the limit once written, or that has more than 100,000 files, is refused then, so that one that packs small (such as a file of zeros) or has very many small files cannot fill the disk. The limit is 200 MB unless more is asked for, up to 1,000 MB. Each step may take 5 minutes. What Git says when it fails is given without the folders of this machine that it names. A request to stop is met while Git works, and keeps nothing.

**Stock is taken.** What is found in the code, by looking at its files (`stock`): how many files and how many bytes there are, and the languages, with the notebooks, the tutorials (notebooks, and scripts in a folder of examples or tutorials, which is what tools are most likely to be made from), whether the README shows its use, the tests, the files that say what to install and whether each version is pinned, the license (by its wording, and by what the project's manifest says), what the README says, whether a GPU is needed (from what it depends on, what its code asks for, and what its README says, and only as an option if the code goes on without one), the data in it or linked from it (with Git LFS pointers and DVC), submodules, and paths that are only on its author's machine. A very large project is looked at within limits on the files, the depth, and the total that is read, and says it was not all looked at (`complete`). Folders that others made (`node_modules`, virtual environments, caches) are not looked in.

**Whether to go on.** `preflight` is a verdict from that stock, made again each time it is asked for, with what the paper has been read to say if it has been read through: **go** if nothing stands in the way, **ask** if there are warnings that a person should look at, and **no-go** if there is a reason it cannot be used. Each of its `checks` says `ok`, `note`, `warn`, `block`, or `unknown`, and why, in words:

- *There is code the sandbox runs*: a block if no code was found, or none of it is Python or R, which the sandbox runs; a warning if less than half of it is.
- *A license to use it under*: a warning if there is none (code with none is not free to use, even if it is public) or it is not recognized; a note for one that is copyleft or for non-commercial use. A license that the paper says the code is under is said beside it.
- *It shows how it is used*: a warning if there is no notebook, example script, or tutorial, which is what tools are made from and what they are checked against (and if only the README shows its use, it says that).
- *Its own tests* (a note if there are none), *what to install* (a warning if no file says, a note if the versions are not all given), and *a GPU* (a block if one is needed, a note if it only can use one).
- *Where its data is* (a warning if its files are kept in LFS or DVC, which are not fetched; found if the code or the paper says where, with whether it can be had not yet looked at; not known otherwise), *examples that read from a place on someone's computer* (a warning, with an example), *submodules* (a note, since their code is missing), and *whether all of it was looked at* (a note if not).

`estimate` is a guess at what making tools from the tutorials (the first 20) would cost in model requests, as a `low` (one request for each) and a `high` (each asked again up to three times with what went wrong), at the price of the model in the settings (a model whose price is not known has none), with `basis` saying what it is a guess from. It leaves out building an environment and running the code, which cost time and not model requests.

**Advice, not a decision.** The verdict is from the files alone. It says nothing of whether the code works, and a person decides. The step `repository` is `done` when code is kept for the agent's address, `failed` when fetching failed, and `pending` when it was stopped.

**What was kept is the address's.** Code that was fetched is of the address it was fetched from. Changing the address, or taking it away, takes the code away; saying it again as it is does not. A fetching that fails or is stopped keeps nothing, and leaves what was there. If the address is changed while the code is fetched (which only an edit of the file can do), the code is not kept.

**The code is data here too.** What is in the project, and what it says, is never taken for an instruction, and is shown as what it says.

## Building the environment

The environment is what the code needs to run: its Python and its packages. It is built as a job (`paperagent-environment`), which can be followed and stopped, from the code that was fetched, and it is built in Docker, where a stranger's install steps can run (a `setup.py` is a program). Nothing of the code is run on this machine, and the paper's code is never run outside Docker.

**From the code's own files.** The recipe is read from the project, and is shown before anything is built. An environment file for conda (`environment.yml`, or another `environment*.yml` or `conda*.yml` at the top) is used first; otherwise `requirements.txt` (or `requirements/base.txt`) is installed with pip, and then the project itself, if it has a `setup.py`, a `setup.cfg`, or a `pyproject.toml` that says it is a package (`[project]` or `[tool.poetry]`). A conda file that does not install the project is followed by its install, without its dependencies. The Python is the one the code says, from `.python-version`, `runtime.txt`, `requires-python` or Poetry's `python`, or `python_requires`, and where it gives a range, the version in it nearest to 3.11 (of 3.7 to 3.13); a conda file that says its own Python has it. Where nothing says, it is 3.11, and the recipe says so. A person can say another version, except for a conda file that has its own. Nothing is guessed from the README: a project with no file that says what to install is refused, and says so (`no_environment`). A project in R (renv or a package), in Julia, with only a Dockerfile, or set up with a Pipfile is refused too, with which it is, since only Python is built. Lock files that are not used (`poetry.lock`, `uv.lock`, `pdm.lock`, `Pipfile.lock`), and a Dockerfile that is beside Python files, are said not to be, so that it is plain how far the environment follows the authors'.

**The build has nothing of this machine.** It runs in a container that is made for it and copied the project into, with no folder of this machine mounted, none of this process's environment passed on (a key in it is not there), and nothing signed in to. It has the capabilities that installing takes (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID`) and no others, `no-new-privileges`, 8 GB of memory (with no swap beyond it), at most 4 CPUs (fewer if Docker has fewer, as it will not make a container that asks for more than it has), 1,024 processes, and a scratch folder of 1 GB. It has the network, since that is how packages are fetched. A test reads what the container is given, and looks from inside it for the workspace and for a key. The time (30 minutes unless said) and the disk the container writes (6 GB) are watched while it runs, and a build that goes over is stopped, and says which. The time is kept to before each of Docker's own steps too, and a stop is met before them. The disk is looked at every 10 seconds, so it is a ceiling that a fast writer can pass before it is seen, and not one that cannot be passed; the scratch folder and the memory are hard. What a build prints is read a line at a time and a line is cut at 4,000 characters, since the project's own code writes what it likes, and at most 4,000 lines are kept. The container is removed however the build ends. It carries a label with the whole of the agent's id, which the image made from it keeps, and a container that a server that was stopped hard left behind is removed at the next build for the same agent, or when the agent is deleted.

**Build, then no network.** What is built is kept as an image, whose id (the hash of its contents) is the pin, with the exact versions that were installed (`pip freeze`, or conda's explicit list with the md5 of each package, and what pip added to it), the image the build started from (its id and its digests), the machine it is for, `pip check`'s verdict, and each step with how long it took. It is then run once as it will be run later, with no network, as an ordinary user, and with a read-only root, and if it does not start there it is not kept. The base images are named by tag (`python:3.11-slim`, `condaforge/miniforge3`), so a build later is the same only if the image is kept: the pin is the image, not the recipe. The image is for the machine's own processor, which the record says.

**A build that fails says why.** The output of the step is read for the likeliest reason, which is one of: `missing_system_library` (with the Debian package that has it, where that is known, which a person can ask to be installed first), `version_conflict`, `python_mismatch` (with a Python to try, where the output points to one), `not_found` (a package that cannot be had for this Python and machine), `network`, `private_dependency` (something that needs a sign-in), `build_failed` (a package with no ready-made version that would not compile), `out_of_memory`, `too_big`, `timeout`, `does_not_run` (it built, but does not start offline), `docker` (Docker did not do what the build needed, as when it stopped answering or the disk was full, which says nothing of the project), and `failed` (none of those). This reads words that package managers do not keep the same, so it is the likeliest reason and not a certainty, and the last lines of the step's output and all of the build's are kept beside it. A failed build leaves no image and no container, and can be tried again, with what it suggested.

**An environment is of one commit.** The image is named from the agent and the commit. Taking the code away, or changing its address, or fetching other code, or deleting the agent, takes the images away too, those that carry the agent's label and not only the one that the record names, so that one that a stopped server left with no record is not kept, and if Docker cannot be asked to, or will not let one go (something may be using it), that is refused (409 `docker`), so that an image is never left with nothing to say it is there. The step `environment` is `done` when an environment is kept for the code, `failed` when the build failed, and `pending` when it was stopped or there is none.

**On the page.** The Environment part shows these things in the same order: the recipe and the form before a build, the job while it goes on (with its output as it prints), and the record or the failure after. The suggestion of a failed build is only offered where it would change the form: a Debian package that is not yet asked for, a Python that is offered and is not the one that was used, or twice the time or disk, to the most that is allowed, for `timeout` and `too_big`.

**How far this has been checked.** That an environment was built and starts is all that is known. It says nothing of whether the code runs, and a test of the code is a later step. A project that installs only by running its own scripts, or that needs data, a GPU, or a system that is not Debian, may build and not work.

## Getting the data

A paper's data is where it says it is: an accession, a link, a DOI of a repository, or a statement of where it is available. What is found is a **candidate**: a place, with the words of the paper that name it (each as a quote with where it is, like any fact of the reading) and whether the code names it too, once the code is fetched. A candidate is only a place. Nothing is asked of it, and nothing fetched, until a person has seen what it holds.

**Only from a short list.** Data is fetched from Zenodo, Figshare, Dryad (listed only: its files are given to people who have an account), the files attached to a GitHub release, Hugging Face datasets, GEO, and ENA (SRA), and from no other place. Each is asked at the hosts it is known by (for Zenodo, `zenodo.org`), by https, with no credentials, at a public address, which is looked at when the connection is made. An address in a paper or a request only says *which* place it is: what is asked is the place's own address, so a link with a login in it, or one that is made to look like a host that is on the list, goes nowhere else. A request that is sent on to another host is followed only to the hosts that the place's files are kept at (Figshare's storage, GitHub's release assets, Hugging Face's, ENA's), every address in the chain is looked at, and one that is not on the list is refused (422 `refused`). ArrayExpress, EGA (which is only given to people who are approved), a project's page on GitHub, and any other host are listed as places the paper names, with why they are not fetched here, and a person gets that data themselves and gives it to the lab on the Data page.

**Listed first.** A person asks a place what it has. It says the files with their sizes, the checksum for each where it gives one (an MD5 from Zenodo, Figshare, and ENA, a SHA-256 from GitHub for files attached since 2025, and from Hugging Face for large files; GEO gives none), and its license where it says one. At most 200 files are listed (50 for GEO, which is asked for each file's size), and it says when there are more. A file that cannot be fetched is listed with why: its address is not at a host that the place may send to, its size is not given, its name is not one that can be kept safely, or the place wants an account.

**Consent.** Files are fetched only when a person names them, says how many bytes they came to when they were shown, and says the most that may be fetched (500 MB unless said, and at most 20,000 MB). The place is asked again, so that what is fetched is what it says now: if the files come to another size than the one that was shown, nothing is fetched (409 `changed`), and nothing is fetched if they are over the limit. Looking at the data, or at a place's files, fetches nothing. At most 100 files are fetched at once; an agent keeps at most 50,000 MB of data in all, and 1 GiB of the disk is left alone.

**Checked as it arrives.** A file is fetched as a job (`paperagent-data`) that can be followed and stopped, one file after another, with the bytes received and the bytes that were said to come, so that what the job says is what was written. A file is refused, and not kept, if it arrives compressed, if it is not the size the place said, if it goes on past it, if it stops short, or if it is too slow to finish in time. If the place gave a checksum, the file is kept only if it has it; a file that does not is discarded, and the message says both values. A file that the place gave no checksum for is kept if it is the size said, and says that it was checked against its size only. Whatever the place says, the SHA-256 of what was received is kept. A file is written where it is kept only after all this, so that a file that was not checked is never in `data/`. If one file of several fails, the others are kept, and the job fails and says how many were, and why not.

**Where it came from.** Each file is kept at `data/<place>/<id>/<name>`, and `data.json` says, for each, the address it was fetched from, when, its size, its SHA-256, and the checksum of the place if there was one, and for each place its title and license. It is only a record of the place's license: whether the data may be used for something is for the person to read. Fetching again a file that is kept is refused until it is taken away.

**Data of one's own.** What a paper used may be had already, or got elsewhere and put on the Data page. A person says which of their own data stands in for a dataset of the paper. It is only a note of which: the data stays where it is, as theirs, and nothing is copied. It is not said to be the same data as the paper's: it is the person's choice of what to use in its place.

**On the page.** The Data part shows these in the order a person goes: the datasets and the places, what a place has, the files chosen with what they come to, the job while it goes on, and what was kept. A file the place gives no checksum for is said so before it is chosen and again when it is agreed to. If a place now has other files than were shown (409 `changed`), or a file was kept since (409 `kept`), the page forgets what was chosen and looks at the place again.

The step `data` is `done` when a file was fetched or data stands in, `failed` when fetching failed and there is nothing, and `pending` otherwise, including after a fetch was stopped with nothing kept. While files are fetched it is `running`.

**How far this has been checked.** That a file matches the checksum that a place gave says that it arrived whole. It does not say that the place's copy is the one the authors used, or all of their data. A file with no checksum is only known to be the size the place said. Nothing of the data is opened, read, or run.

## Running the tutorials

A tutorial is the nearest thing a project has to a statement of how its code is used, and what it prints and writes is what the authors' code does with the inputs they chose. Running each in the environment that was built, and keeping what it did, gives later steps something to compare with. This is the **reference run**. It shows that the tutorial ran here, and what it gave. It does not show that what it gave is right, or that it is what the paper reports, and nothing here says it does.

**Which are run.** The tutorials that stock found (scripts in a folder of examples or tutorials, and notebooks; at most 25 are listed) that are Python. A script is run as it is, and a notebook as the code of its cells, one after another in one namespace. A tutorial in R, Julia, or the shell, an R or Quarto document, and a notebook in another language are listed with that as the reason, and are not run. The first 10 are run unless more are asked for (at most 25), and those that were not run are listed with why.

**Each is run in a container of its own**, made from the image of the environment, with the same care as a build and more: no network, a root that cannot be written to, no capabilities, `no-new-privileges`, 8 GB of memory, at most 4 CPUs, 1,024 processes, a scratch folder of 1 GB, and no file larger than 256 MB. Nothing of this machine is in it but a folder of its own, which the project is copied into, since a tutorial writes beside itself; the copy in the image is not changed. The data that was fetched is given to it to read only, at `/opt/paper/data`, with `PAPER_DATA` saying where, unless it is asked not to be; data that only stands in by a note is not given. A run has 10 minutes unless said (at most 60), all of the runs have 30 (at most 240), and what one writes is watched every 5 seconds and the run stopped at 2 GB unless said (at most 20), counting the copy of the project; the runner ends itself 30 seconds after its time as well, in case the server is not there to. A container that a stopped server left is removed at the next run for the agent, when the environment is taken away, and when the agent is deleted. A call that a conversation makes of one of the agent's tools is in a container named differently (`virtual-lab-call-`, where a run's is `virtual-lab-run-`), which a job that begins does not take away, so that it does not end a call that is going on; one that a stopped server left is taken away only when the environment is taken away or the agent is deleted.

**What is recorded**, by a small script of ours (`tutorial_runner.py`, which needs nothing but Python's own library, and runs under Python 3.7 and later), and not by the authors' code: what each cell printed and its last value, how it ended, and the traceback if it did not; every call that the tutorial makes into the project's own public functions (not those the project calls itself, and not generators), with the arguments and the result, at most 100 calls and 4 of each function, with how many were seen (`calls_seen`); and the files it wrote (path, size, SHA-256, and whether it was new; at most 200), of which those of at most 1 MiB (20 MiB for each tutorial) are kept, from the first run. A value is kept as itself if it is plain (numbers, strings, lists and dictionaries of them; a number that is not finite is kept as `{"$float": ...}`), and otherwise as its type, its text, and, for arrays and tables, their shape, their type, a hash of their content, and the first values. Magics and `!` lines in a notebook cannot be run as Python: they are left out, and each cell says which.

**Run again, to see whether the runs agree.** Each tutorial is run twice unless said (at most 3, as time allows), because a reference that two runs do not agree on is not one to hold anything to. What is compared is what later steps rely on: the calls (the function, the arguments, and the results) and the files written. What was printed is compared and said (`differs`) but does not decide, as it holds timings and progress bars. `stable` is `true` if the runs agree, `false` if not, and `null` if there was nothing to agree on (a tutorial that called nothing of the project's and wrote nothing) or it was run once.

**When one does not run.** It says why as far as what it printed can tell: it needs the network (`needs_network`), a file it reads is not there (`missing_file`; fetch the data first), something it imports is not installed (`missing_package`; the environment is made of what the authors' files list), it asks for a GPU (`needs_gpu`), it uses what only a notebook's own kernel has (`needs_notebook`), the notebook could not be read, it ran out of memory, it was not finished in time (`timeout`), it wrote more than is allowed (`too_big`), it ended without saying how (`no_result`), or it raised an error (`error`). The others are still run. If Docker itself does not run a tutorial, that is the job's failure, and is not put down to the tutorial.

**What is not trusted.** The tutorial runs in the same process as what records it, so what it writes of itself is read as data: it must be of the shape the runner writes, within the sizes and the counts (calls, files, cells) and the depth of nesting that the runner keeps to, and a file that it says it kept is kept only if it is a plain file of the size and the hash that were said, reached without a link. Code that means to deceive its recorder could make the record say what it likes. The container is what keeps it from harming this machine; the record is not a proof against code that cheats.

**It is of one commit and one image.** The account is kept in `checks/`, tied to the commit of the code and the image that the environment is, and goes with them: taking away the environment, the code, or the agent takes it away. Each tutorial's record is written before the account names it, so that the tutorials that were finished before a run was stopped are kept, and says that the run did not come to its end (`complete` is `false`). The tutorial that was being run when it was stopped is not kept, as its runs were not all done. The step `tools` is `running` while the tutorials are run, and is `pending` afterwards, until tools are made; it is `failed` if the job failed with an error, until that is cleared.

**On the page.** The Tutorials part shows, in the order a person goes: the plan (which would be run and which would not, with why) and the form before a run, the job while it goes on (with its output as it prints), and the account after, with each tutorial's status, whether its runs agreed (`The same each of 2 times`, `Not the same each of 2 times: the calls to the code differed`, `Run once, so not compared`, or `Not compared, as it did not end`), and what it kept. The record of one tutorial is fetched only when it is asked for (`GET /api/paperagents/{id}/reference/{tutorial}`). While a run goes on, what it has kept is not shown, as it is not yet a run that ended. A run that was stopped is shown as not run to its end, with the tutorials that were finished before it, and the form is shown again, as the next run replaces it. The page asks that the time for all of the tutorials is not less than the time for one, which the server does not: it would run them, and end the run when the time for all is used. If the server says the tutorials have been run (409 `done`) or the image is no longer in Docker (`image_missing`), or a tutorial's record is gone (404), the page looks at the agent again.

**How far this has been checked.** That a tutorial ran here, offline, in the environment that was built, and gave what is kept, and that two runs agreed or did not. Not that it is what the paper reports, that the results are correct, or that the code does what the paper says. A tutorial that needs data that was not fetched, the network, or a GPU does not run.

## Making tools

Each function of the code that a tutorial called is a candidate for a tool. A tool is a **wrapper**: a small function, written without a model, that takes the same parameters as the paper's function, calls it, and gives back what it returns. It holds no algorithm of its own. Where the code's type hints are fit for a tool they are the wrapper's, and where they are not, the types of what the tutorial passed are, and where they are not either, the parameter may be anything; only how a wrapper is written is repaired (up to `repairs` times), never what it calls. A wrapper is checked, before it is called and every time it is read back, to import one module of the code and call one function of it with its parameters and nothing else.

**Which functions.** Those that the tutorials that ran to their end called, at module level, with arguments that are plain data (numbers, strings, lists and dictionaries of them) that were passed by name or position to a function with a fixed list of parameters, and that returned. A method of a class, a function defined inside another, one that takes `*args` or `**kwargs`, and one that has more than 40 parameters are not made, and nor is one whose code cannot be found in the project, from the name of its module (the file that a record names is not taken, as the record is written by the tutorial's own process), or is not the function that was called. A call that raised, or was passed an object that is not plain data, is left out of what the tool is held to, and said. The tutorials that did not run to their end are not held to. Each function that is left out is listed, with why.

**Each call is made again** in a container made as the tutorials' were, from the same image, with no network, a root that cannot be written to, and the limits above, and with the data if the tutorials were given it. It is given the arguments that the tutorial passed, from the folder that the tutorial made the call from, and not what the tutorial got. Each call is made in a process of its own, on a copy of the project of its own, as many times as `repeats` says, so that one call leaves nothing for the next and a function that counts its calls, or reads what an earlier call wrote, is found out. What came back is compared with what the tutorial got: numbers within a relative tolerance of 1e-6 and an absolute one of 1e-9, other values exactly, a whole number and a float as different, and arrays by their shape, their type, and their values within the same tolerance (by their hash, exactly, when only a hash was kept). A value of which only how it shows itself was kept is compared by that only if it is all of how it shows itself: one that was cut short, an object that shows only its type and where it is in memory, and an array or a table that was too big to be hashed cannot be told from another that looks the same, so a call that gave one is not held to be what it was, and its tool is left out with that said. What was printed is not compared.

**Tier A.** A tool of which every call gave what the tutorial got, every time it was made again, is of tier A. That is all that tier A says: that the tool calls the authors' own function, and gives again what the tutorial's run gave for the arguments the tutorial passed, within the tolerance. It does not say that what it gives is right, that it is what the paper reports, or that it gives the right answer for other arguments, and it is not independent of the tutorial, since what it is held to is what the tutorial got. The evidence is kept with each tool: every call, its arguments, what the tutorial got, what each repeat gave, and the tolerance.

**A function that does not hold is dropped**, with what happened: it raised when called again (with a hint where the error says that it may read a file or set a value that the tutorial made before the call), it gave something else (with what it gave), a call took more than the tool was given, or the time for all of the tools was used first. It is not rewritten until it passes, and it is not asked of a model. A function that depended on something the tutorial set up before it, such as a file that the tutorial wrote, will be dropped, and that is as it should be: the tool could not be called on its own.

**It is of one commit, one image, and one reference run.** The tools are kept in `tools/`, with an account in `checks/tools.json` tied to all three, and go with them: taking away the tutorials' run, the environment, the code, or the agent takes the tools away, and running the tutorials again does as well. Each tool is written before the account names it, so that the tools that were made before a job was stopped are kept, and the account says that the making did not come to its end (`complete` is `false`). The step `tools` is `running` while they are made, `done` if a tool was made, `failed` if the job failed with an error or no tool held, and `pending` if it was stopped or the tools were taken away.

**On the page.** The Tools part shows, in the order a person goes: nothing but a request to run the tutorials first, until they have been run to their end (`reference` is `null`); then what would be made (the functions that can be, each with how many times it was called and in how many tutorials, and the functions that cannot, with why and what the check found) and the form before the making; the job while it goes on (with its output as it prints); and the account after, with each tool, the functions that were not made, what was allowed, and what the tools do and do not show. If no function that the tutorials called can be made into a tool, the page says so and shows why, and has no form. A tool's wrapper, signature, and evidence are fetched only when they are asked for (`GET /api/paperagents/{id}/tools/{name}`). While the tools are made, what is kept is not shown, as it is not yet a making that ended. A making that was stopped is shown as not made to its end, with the tools that were finished before it, and the form is shown again, as the next making replaces it. The page asks that the time for all of the tools is not less than the time for one, which the server does not. If the server says the tools have been made (409 `done`), or the tutorials are not run (`no_reference`), or the image is no longer in Docker (`image_missing`), or a tool is gone (404), the page looks at the agent again. The step `tools` is `running` while the tutorials are run and while the tools are made, and the page tells the two apart by the job.

**How far this has been checked.** That each tool calls the authors' own function and gave again what the tutorial's run gave, within a stated tolerance, when called alone in a fresh copy of the code, offline, in the environment that was built. Nothing says that the result is correct.

## Checking the tools

A tool of tier A gave again what its tutorial got, for the arguments the tutorial passed. The tutorial is both the source and the test of that, so it shows little. **Tier B** asks for kinds of evidence that the making of the tool did not produce, against two different bases (what the kind holds the tool to: the code's own function, the code's own tests, or the paper's numbers): a tool that has a check that passed against each of two bases, and failed none, is of tier B. Two kinds that hold the tool to the same basis are one basis: the inputs that a rule changes and those that a model chose both call the tool and the code's own function, so both passing is one basis, and not tier B. Each kind ends as **passed**, **failed**, or **not obtained**: a check that could not be made, such as one for a function that no test calls, is not a failure, and is not evidence either. These are made when the person asks, one tool after another, each in a container as the tool's calls are, from the image of the environment, with no network and the same ceilings, and each is kept as it is made, so that a job that is stopped keeps what it had made.

- **Inputs the tutorial did not use** (`heldout`). The arguments of up to three of the calls that the tutorial made are changed, every second item of a list of four or more taken away, and every number moved a little (a whole number by one away from nothing, a fraction by a tenth less, any other number by a tenth more). Text, truth values, and numbers that are not finite are left. Both the tool and the code's own function, which is imported from the project by a caller that is not the tool's wrapper, are called with each changed set, each call in a process of its own on a copy of the code of its own, as many times as `repeats` says. They must give the same within the tolerance the tool was held to, and the same each time. If the tool gave anything else than what the code's own function gave, the kind **fails**; if some calls gave the same and none gave otherwise, it **passes**. A call that stopped with the same error from both, a call that the code's own function gave something else for each time it was called (which cannot be held to anything), and a call that was not made in the time are neither for the tool nor against it, and are said; if none gave the same, nothing is obtained. A tutorial that passed no number and no list of four or more has nothing that can be changed.
- **The code's own tests** (`repo_tests`). The tests in the code that call the function are found by reading the files of tests, and never running them: those named `test_` at the top of a file, and those of a class of tests or of a `TestCase`, up to 25. A test is found only if it names the function by what its file imported for it, from the module that defines the function or from a package above it (`from pkg.core import run`, `from pkg import run`, `pkg.core.run(...)`, or a relative import of that module), so that a test of another library's function of the same name (`np.mean`), or of another module's, is not taken for it. These are tests of the code's function: the tool's wrapper is not called in them, so this kind shows that the function works in this environment, and not that the tool does. Only the check with inputs that the tutorial did not use calls the tool. They are run by `pytest` in a copy of the project, in the environment, with no network, if `pytest` is in the environment, and nothing is installed. If any test did not pass the kind **fails**; if all that were run passed, it **passes**; if there is no test for the function, `pytest` is not in the environment, the tests could not be run to their end, or all were skipped, nothing is obtained. A test that calls the function through another function is not found.
- **Numbers the paper reports** (`paper_numbers`). The numbers that the reading of the paper kept as claims are looked for, by a program, in what the calls of the tutorial gave (the first ten calls of a tool, and every number inside a result that is plain data, to a depth of eight). A number is looked for only if it has digits enough to be told from chance (three, or two with a decimal point) and its rounding is narrow for its size (half of its last place is within one percent of it): `0.93`, `9.5`, `1.25`, and `104` are, and `5`, `12%`, `0.05`, `1.0`, `2.5`, and `0.10` are not. A number that a call gave is the number written if it rounds to it, within half of the last place that the paper wrote, and a number written as a percentage is also looked for as a part of one (`93.1%` is `0.931`); nothing is allowed beyond the paper's own rounding. Where it is found, that is a candidate: a claim, a call, and a place in its result. A number that is in more than two places of one result is passed over, as it is too common there to say anything, a key of a result that is longer than sixty characters is not followed, and at most twenty candidates are put to the model for one tool. The model is then asked one thing for each candidate, with the paper's sentence, the call, and the place: whether the sentence reports the quantity that the result holds there. It can say yes to a candidate that was found, and to nothing else: a number or a place that it adds is thrown away, a candidate that it answered twice or not at all is not accepted, and what the paper's sentences say is given to it as material between tags that cannot be closed from inside, which it is told is not instructions. Which candidates it accepted are kept, with its name and what asking it cost, as what they are: a model's reading of the words. The tool is then called again, as many times as `repeats` says, with the arguments of each call that an accepted candidate is of, and what it gives at the place is compared with the number as written by a program, with no model. If it gave another number, or none, at any call, the kind **fails**; if it gave the number every time at one or more places and gave none other, it **passes**; if there is no number to look for, none was found, the model said no to all, the model could not answer, the calls stopped, or were not made, nothing is obtained. What the model costs is limited by `max_cost`, which is looked at before every request, so that the one request that is going can take a little more than is left; when it is reached, or when a response does not say what it used so that the limit can no longer be kept, this kind is not made for the tools that are left, and the others are. A request that fails (a key that is refused, a connection that is lost) ends this kind for that tool, with the reason, as nothing obtained. The check is bound to the numbers that were read, by a hash of each number and its sentence, so a paper that is read again, and gives other numbers, leaves it stale. It is of the arguments that the tutorial passed, so it is not independent of the tutorial in what it calls; what is independent is the paper, which did not see the tool, and what the tool gave.
- **Inputs that a model of another family chose** (`verifier`). A model reads the tool's wrapper, the code of the function (with its decorators, up to 8,000 characters), and the arguments of up to three of the calls that the tutorial made, and proposes inputs for which the tool and the function might give something else: a default that the wrapper gives, a parameter that is left out, a value at the edge of what the function accepts, an empty list, zero. It is of another family than the model in the settings (`openai`, `anthropic`, `google`, `meta`, `mistral`, `deepseek`, `qwen`, `xai`, `cohere`, as the name of the model says, and through OpenRouter as the maker in its name says), so that it does not share that model's blind spots; a model whose family is not known is refused, and not taken for another, and so is one of the same family, which is told before anything is made. What it proposes is data. Each input is a JSON object of arguments by parameter name, which a program parses and keeps only if it is not too long (2,000 characters), has no name that the tool does not take, has every parameter that has no default and every one that the function takes by its place, has values of the types that the tool's signature says (a number that JSON does not have is refused), is not what the tutorial passed, and is not another that is kept; at most six are run. What is refused is kept, with why. The tool and the code's own function are then called with each input that was kept, each call in a process of its own on a copy of the code of its own, as many times as `repeats` says, by the same program as for `heldout`, which judges whether they gave the same, with no model: the kind **fails** if the tool gave anything else than what the code's function gave, **passes** if some gave the same and none gave otherwise, and nothing is obtained if none could be run or compared. A model cannot say that a tool passed or failed; it can only choose what is tried, and an input that is not what the tool can be given, or is what the tutorial passed, is not run. What it says of where the wrapper and the code might differ is kept as its words (up to five, each cut to 300 characters), and is no part of how the check comes out. What the model is shown is between tags that cannot be closed from inside, with a prompt that says that it is material and not instructions. What it costs counts against the same `max_cost` as the check against the paper's numbers: both are given one record of what was used, so when the limit is reached the kinds that ask a model are not made for the tools that are left, and the others are. A request that fails ends this kind for that tool, with the reason, as nothing obtained. It holds the tool to the code's own function, as the inputs that a rule changes do, so it is the same basis for tier B as those, and its use is that it looks where a rule does not: it can fail a tool that the rule's inputs passed, and it can pass a tool for which the rule found nothing to change.

**Tier B follows from what is kept, and from nothing else.** The checks are kept in `checks/independent/<tool>/<kind>.json`, each bound to the hash of the tool's wrapper, the commit, the image, and the reference run that it was made of. A tool is of tier B only if it is of tier A, checks against two or more different bases passed, none failed, and all of those are bound to what is kept now (and, for the paper's numbers, to the numbers that are read from the paper now). A check that is bound to something else is shown as stale and counts for nothing, either way: a tool whose wrapper was rewritten has no tier B until it is checked again, and a check that failed earlier does not hold back a tool that has been checked since. A model says nothing that is kept here that counts, other than its answer, with its name, of whether a place that was found is the quantity that a sentence reports, which can only make a candidate that a program found count for the check, and which the tool must then give again; and the inputs that a model of another family chose, which a program keeps or refuses and runs, and judges. The tier flows to what a conversation is given: a tool's description says `[Tier B]`, which kinds passed, and that this does not show that what it gives is right, and the agent is of tier B if it has a tool of tier B. Taking away the tools, the reference run, the environment, or the code takes the checks away; so does `DELETE /api/paperagents/{id}/checks`, which leaves the tools at the tier they were made as.

**How far this has been checked.** That the tool gives what the code's own function gives for other inputs, that the authors' own tests of the function pass in the environment, and, if they were asked for, that the tool gives a number that the paper reports for the arguments of its tutorial, where a model said that the paper's sentence is about that place, and that it gives what the code's function gives for inputs that a model of another family chose. Not that what it gives is right, that it gives the paper's numbers for other arguments, that the number is not the same by chance, or that the tests prove anything: they are what the authors chose to check, and the changed inputs are made by a rule, or chosen by a model that read the wrapper and the code, and not by anyone who knows what the function should give. Only a number with digits enough, in a result that is plain data and a few places, is looked for, so a paper whose numbers are few, or are all of results that the tools do not give, has nothing to be checked this way, and that is said and is not a failure.

**On the page.** The Checks part, after Tools, shows each tool with the tier its checks come to now, and says the tier it was made as, which kinds passed and what they were against, and, for a tool that is not yet of tier B, what it would need: a check that passes against a basis it has not passed one against. The tier is a button that opens how each kind of check went (`passed`, `failed`, `not obtained`, `stale`, or `not made`, in words, with what it was against and when it was made), and what each was made of (the calls that were changed or proposed, and how each went; the tests that were run and those that did not pass; where the paper's numbers were looked for) is fetched only when it is asked for (`GET /api/paperagents/{id}/checks/{name}`). What a model said of where the wrapper and the code might differ is marked as its words. The form offers each kind with what it is against and, for those that ask a model, says so: it asks what the model may spend, and, for the check with inputs that a model chose, which model does, and the server says if that is of the same family as the model in the settings or of one whose family is not known. A kind that cannot be asked for says why (the paper has no number to look for, or it is not known whose model the one in the settings is). While the tools are checked the job is followed and may be stopped, what is kept is shown when it is over, and nothing else is done to the agent, and its paper is not read. A check that is stopped keeps the checks it had made. Neither the page nor the server asks that the time for all of the checks is not less than the time for one: a total that is less ends the checking when it is used, and the checks that were not reached are said not to have been made. Taking the checks away asks first, and leaves the tools at the tier they were made as, which the Tools part says as "Made as tier A". If the server says the tools are not there (`no_tools`), the tutorials are not run, or the image is no longer in Docker, or a tool's checks are gone (404), the page looks at the agent again.

## Trying the claims

The tutorials of the code were run, and what they gave was kept (see Running the tutorials). **Trying the claims** holds each thing that the paper reports to what they gave, to say whether the code gives it. Nothing is run for this: the claims are held to what the run of the tutorials kept, which is the calls into the code with what each was given and gave, and the lines that each printed or a notebook's cells showed. It is done when the person asks, as a job that can be stopped, and what was done is kept after each request to a model, so that a job that is stopped keeps what it had. It is in steps, each held to what it can be:

- **Which claims are tried** is a program's say. Only a claim that is a number, written plainly, with digits enough to be told from one that is the same by chance (the same rule as for the check against the paper's numbers) is tried. A comparison, a statement in words, a number that is not written plainly (digits with a point, commas in threes, a sign, or a percent sign are plain; a range, or a number with words or units in it, is not), and a number with too few digits are listed as **not attempted**, with why. At most 300 claims are listed and at most 100 of them are tried at once; the others are counted or are not attempted, and say so.
- **Where the code might give it** is found by a program, in two ways: the places in what the tutorials gave whose value rounds to the number as the paper wrote it (within half of its last place, and a number written as a percentage is also looked for as a part of one), in a call's result or in a printed line; and the named results (a key, or a function's own result, or a printed line with words in it) of a tutorial that refers to the same figure or table as the sentence does, which is read from the tutorial's path and its words (`Fig. 3`, `Figure 3`, `Figures 2 and 3`, `Table S1`; a panel is not part of a label). A number that is in more than two places of one result, or of one tutorial's printed lines, is too common there to say anything, and those places are left out. A claim that has no place at all is not attempted: **not run** if a tutorial that it refers to was not run (it was in R, or did not run to its end, and the reason is given), **nothing to compare** if one that it refers to gave no named number, and **no code** if no tutorial refers to a figure that it does and none gave a number that rounds to it. A claim that no code could be linked to is not failed, as nothing was tried.
- **Which place the sentence is about** is the only thing that a model is asked, a few claims at a time. It is shown each sentence and the places by name (the call with what it was given, with any number that is one the call gave shown as #, and where in its result; or the printed line with each number in it masked), and not their values, in an order that is fixed by what each place is and not by whether its value rounds to the number, so that it cannot choose the place that agrees with the paper and make a claim reproduce by its choice. It can choose a place that was found and nothing else: a place that it adds, a claim that it answered twice or not at all, and an answer of none (it is told to answer none unless it is sure) leave the claim not attempted (`no_quantity`). What the paper says is given to it as material between tags that cannot be closed from inside, which it is told is not instructions. What it costs is limited by `max_cost`, looked at before every request; when it is reached the claims that were not asked are not attempted (`limit`), and a request that fails leaves the claims of that request not attempted (`no_answer`), with why.
- **The comparison** is a program's. The value that was kept at the place that was chosen is held to the number as the paper wrote it. **Reproduced**: it rounds to the paper's number, as the paper rounded it, and the runs of the tutorial did not disagree with each other (they agreed, or it was run once, or they could not be compared, which the summary says). **Partly**: it is within 5% of the paper's number and does not round to it, or it rounds to it and the runs of the tutorial did not agree with each other, so it may not be given again. **Not reproduced**: it is another number. Each is kept with what it was held to (the `link`): the tutorial, how many times it was run and whether the runs agreed, the place, the value that was kept, how far it is from the number and as what it was read, whether the place was found by its number, by the figure that the sentence and the tutorial both refer to, or both, the model that chose it, and up to three other places that hold the number.

The account is `checks/reproduction.json`, and it is bound to the commit, the image, and the run of the tutorials that the claims were held to, and to a hash of the claims with their sentences. One that is bound to something else (the paper was read again to other claims, or the tutorials were run again) is shown as `stale`, with what it `was`, and counts for nothing; one that is not in the shape that is kept is not an account. A claim that the account does not have is listed as not attempted (`not_tried`). Taking away the run of the tutorials, the environment, or the code takes the trying away, and running the tutorials again begins without it; the agent's paper cannot be read, nor its tutorials run, while the claims are tried.

## Where a claim parts from the paper

A claim that did not reproduce is not shown to be wrong, and a person who sees it will ask where it parts. **Looking at where** is made each time it is asked for, from what is kept, by a program, with nothing run and no model asked, and nothing of it is kept of its own: it is of the trying of the claims when that is of the run of the tutorials and the claims that are kept now, and is not shown (`stale`) when it is not. It is of each claim that was not reproduced, and each that was partly, in two ways:

- **The first point at which the tutorial parts from a number the paper states.** The calls that a tutorial made are in the order that it made them, and each claim of the paper that was held to one of them agreed there or did not, so what is named is the first output, in that order, whose number does not round to the one that the paper gives for it, with what it gave, what the paper says, and where it is. The outputs before it that agreed are named (the last five, and how many there were), as the tutorial agrees with the paper as far as they go. A place in a line that a tutorial printed has no known order among its calls, so it comes after them, and is said to. A claim that is partly only because the runs of the tutorial did not agree has a number that rounds to the paper's, and so has no point.
- **The differences that were found between what the paper says it used and what was used here**: a version of Python or of a package that the paper names (read from the paper's resources, which are of a plain version only, and held to the installed one as far as the paper gives it: 1.4 is the one that 1.4.2 is of) and the one that is installed according to the environment's lock; data that the paper names when none was fetched and given to the tutorials; runs of the tutorial that did not agree, and no seed set in the tutorial's own text (`np.random.seed`, `random_state=`, `manual_seed`, and so on), though what it calls may set one; and a number that the paper gives for an argument by its name (`n_neighbors = 30`, `a resolution of 0.8`) when each number that the paper gives for it differs from the one that a call up to the point was given. Software that is not installed under the name that the paper uses, or is of another language, is listed as not installed and is not a difference.

**A difference is one that was found, not a cause.** Nothing was changed and run again to see whether the number came back, so none is said to be why it did not. That none was found does not say that there is none: what the paper does not say, the code's own defaults (only what a call was given is seen), what is installed under another name, and the data that the code downloads itself are not seen.

**How far this has been checked.** That the tutorials of the code, as they ran here, in the image that was built, gave a number that rounds to the paper's at the place that a model said the sentence is about, or did not. Not that the tutorials were run on the paper's data (only data that was fetched and given to the run, if it was, is that, and nothing here says that it is what the paper used), that a quantity of the same name is the one that the paper means (a model judged that from words), that a number that is the same is not so by chance (a number with few digits is not tried, and one that is in many places is left out, and a few may still be), or that the paper is right. A claim that did not reproduce is not shown to be wrong: the code, the data, the seed, a package, or a default may differ. Where it first parts is looked at above, and says only where, and what differs that was found, not why.

**On the page.** The Claims part, after Checks, shows, in the order a person goes: what is wrong with trying the claims (the paper is not read, it reports no number with digits enough, or the tutorials are not run, each as the server says it), the job while it goes on, what was kept, and the form. While the claims are tried the job is followed and may be stopped, the form and what was kept are not shown, and nothing else is done to the agent, and its paper is not read. A trying that is stopped keeps the claims it had come to, and the rest are listed as not tried. What was kept is how many claims came out each way, which model was asked, how many times, what that cost, and whether it came to its end, then a table of the claims, each with its sentence, its number, how it came out in a word (not only by colour), and what that came to in words. The table can be told apart by how the claims came out, and saved (`GET /api/paperagents/{id}/tables/claims`). A claim that was held to a place has a button that shows what it was held to (the place, what it gave and what the paper reports, how the place was found, that the model chose it without being shown any value, whether the runs agreed, and the other places that hold the number), and one that did not reproduce, or only partly, also where the tutorial first parts from the paper and what differs that was found, marked as found and not shown to be why. What differs of the whole run (the software that the paper names against what is installed, and the differences that are of no one claim) is shown under the table. When what was kept is of another run of the tutorials or other claims than are kept now, the page says so, and each claim is shown as stale with what it was and nothing of what it came to, nor of where it parted or what differed. The form asks the most that the model may spend, which must be said; trying again does not ask first, and takes the earlier trying and the variants that were made of it away; taking the trying away does ask. If the server says the paper is not read, has no number to try, or the tutorials are not run (422 `no_claims`, `no_numbers`, `no_reference`), the page looks at the agent again, as it does when the paper, the code, the environment, the data, the tutorials, the tools, or the checks change.

## Variants

A person who sees a claim will want to know what the number would be if the analysis were a little different: another threshold, another setting of a test. **A variant** is that: the call that the claim was held to is made again, in the environment, with the arguments that the person named changed and nothing else, and the number at the same place in what it gave is read. Nothing is asked of a model.

- **What is made.** The call of a tutorial that the claim was held to, as it is recorded (the arguments it was given, as plain data), is made as the code's own function, alone, by name, in a container of the image of the environment, with the tutorial's data if it had any, with no network, in a process of its own on a copy of the code, as many times as the person said (2 if they did not). It is not a tool's wrapper, and nothing else of the tutorial is run. Only a claim that was held to a call is varied: a line that a tutorial printed is not a call that can be made again.
- **The call with nothing changed is made first, in the same way.** It is held to what the tutorial got, as a tool is. If it gives that, the variant is **comparable**. If it does not (it may rely on what the tutorial set up before it), or it stops with an error, the variant is still kept, and says that the call alone does not stand for what the tutorial did, so that what it gave cannot be held to what the tutorial got.
- **What a variant says** is a number at a place, and what it was held to: what the claim was held to, what the tutorial's call gave there, what the variant gave, and what the paper reports. It says if that number rounds to the paper's, and that is **not a reproduction** of the paper's result: the analysis is not the paper's. A variant that gave no number at the place, gave something else each time, stopped with an error, or was not made in the time says that. None says why a number came out as it did.
- **It is never the paper's result and never changes the claim's.** A variant is kept in `checks/variants.json`, which is a file of its own: nothing is written to `checks/reproduction.json`, so what was said of whether the claim reproduced is as it was, and each variant says so in its last sentence. The most that are kept is 100, the oldest going.
- **What it is bound to.** The commit, the image, and the run of the tutorials, the claims with their sentences, and the trying of the claims that the claim's place was found in. Variants that are bound to something else are not shown, and the next one that is made replaces them; a file that is not in the shape that is kept (a status that is not one, a variant said to be comparable when its control did not match, a text that does not end with what a variant is, more than five changes, a changed value that is not plain data) is not used.

**How far this has been checked.** That the code's own function, called alone with those arguments in the image that was built, gave that number at that place. Not that the call alone is what the tutorial did unless the call with nothing changed gave what the tutorial got, not that the changed analysis is a sensible one or the paper's, and not that the number is right. Only claims that were held to a call, with arguments that are plain data, of a function that can be called alone (not a method, not a function inside another, not one that takes `*args` or `**kwargs`) are varied.

**On the page.** The Variants part, after Claims, follows the making of a variant while it goes on, says what is wrong, if anything is (the claims are not tried, or what was tried is of another run of the tutorials or other claims than are kept now, each as the server says it, and no form is offered then), and shows the variants that were made and the form. While a variant is made the job is followed and may be stopped, the form and the variants are not shown, and nothing else is done to the agent, and its paper is not read; one that is stopped keeps nothing. The form asks for a claim, among those that were held to a call that can be made again (the others are listed with why, when that is asked for), and shows the arguments that call was given, each as it was, with a place for what it is to be instead. A new value is written as JSON (text in double quotes, a number, `true`, `false`, `null`, or a list or table of those) and an argument with nothing written is not changed; a number with no point is sent as a whole number, so the page cannot give `1.0` in place of `1`. An argument that is not plain data is shown and cannot be changed. The form also asks how long both calls may take, how many times each is made, how much one may write (up to what the server says, with what it uses if they are left as they are), and, if wanted, a note. What is wrong with what was asked (no argument changed, more than five, a value that is not JSON or that the argument already had, a limit that is not a whole number within what the server takes, a note that is too long) is said before anything is sent; what the server refuses is said as it says it, and when it says that the claims are not tried, the tutorials are not run, or what was tried is stale (422 `no_reproduction`, `no_reference`, `not_tried`, 409 `stale`) the page looks at the agent again. What was typed stays after a variant is made, so that it can be changed a little and made again, and starts over when another claim is chosen, or when the claim is offered with other arguments than the ones it was typed for, as it is when the claims are tried again. Each variant is shown with the words that it is not the paper's result, how it came out in a word and not only by colour, what was changed, what the call gave with the change beside what the call that the claim was held to gave, whether it is comparable and, if not, why, whether the number rounds to the paper's (which is said not to be a reproduction), and the note. A button shows how it was made: the server's account in words, what each time it was made gave, where the call with nothing changed parted from what the tutorial got or stopped, and what counted as the same number. The variants can be saved as a table (`GET /api/paperagents/{id}/tables/variants`), and taken away after asking; trying the claims again, or taking the trying away, takes them away too. Variants that are of another run or trying are not shown, and the page says how many are kept.

## Tables

What the claims came to can be saved as tables, in the way that what a survey of papers found can be, to open in a spreadsheet. They are made each time from what is kept, with nothing run and no model asked, and nothing is kept of them. The Claims part of the page links the table of the claims, and the Variants part the table of the variants.

- **Claims.** A row for each claim that the trying lists, in the order that the paper has them, which is the first 300 (the most that are listed and tried, and the `more` of `GET /api/paperagents/{id}/reproduction` says how many come after; the table does not): its id, the number that the paper reports, its sentence, its status, why it was not attempted (in words), what it came to, the tutorial, the call, and the place that it was held to, what the tutorial gave there, where it first parts from the paper and what differs that was found (for a claim that did not reproduce, or only partly), and how many variants were made of it. A claim that is stale is listed as stale, with what it was, and nothing of what the earlier trying said of it.
- **Variants.** A row for each variant that is shown, which is those of the trying that is kept now, in the order that they were made, beside what came of the claim itself, which a variant does not change: what was changed (each value in full), how the call with nothing changed went and how the variant did, the number that the tutorial's call gave, the number with nothing changed, and the number that the variant gave, whether it is comparable and whether it rounds to the paper's number, the note that was made with it, and what it came to in words, which ends by saying that it is not the paper's result. A column says it too: it is "No" under "Is it the paper's result" for every row.
- **To be opened safely.** What a paper says, and what a person wrote, may begin with `=`, `+`, `-`, or `@`, which a spreadsheet would read as a formula, so such a cell has a quote put before it, as it has in the tables of a survey.

## Writing the method from the paper (tier C)

A paper that has none of its code can still have a method that can be called, if the person asks for it: a model reads the words of the paper that describe the method and writes a Python function that does what they say. What is written is a **re-implementation**, and is shown as one wherever it is shown, and it is never of tier A or B, which are of the authors' own code.

It is offered only for a paper that has been read and that reports at least one number with digits enough to be told from one by chance, which is what the function will later be checked against, and not for an agent that was imported (what it can do is what its server does) or that has tools of the authors' code (which are the method as they ran it).

The person is shown exactly what the model would be given before anything is written. The words of the paper are chosen by a program and never by the model: the sections the person names, or those whose headings say they are of how something was done if they name none and search for nothing, and the places that a search for words finds, at most 8,000 characters of them, cut where a paragraph or a word ends and said to be cut, each said to be from its section and page. With them go the paper's title, what the person says they want of the function in their own words, and the name it will have, which is made of the paper's title unless the person says it. What is shown has a key, a hash of the words, the name, the model, the paper's file, and what is said of what a re-implementation is; agreeing is sending that key back, and a key that no longer fits, because the choice, the model, or the paper changed, is refused as `changed`, so that nothing is written that the person did not see.

The model in the settings is given those words and nothing else of the paper, and is told to do what the passages say, to say in a comment where it chose what they leave out, not to use what it remembers of the authors' own code, to use the standard library only, and never to put a number that the paper reports as a result into the code, its comments, or its docstring. What it writes is read as Python and imported in a container with no network, which shows that it is a function that can be a tool, and says nothing about what it gives. What is kept is the function and a record of the writing: the key that was agreed to, the model, what it cost against the limit that was said, how many attempts it took, and why it failed if it did. The record is bound to the paper's file, so that a function written from one paper is not shown as of another that took its place.

**A function that was written has not been checked against anything of the paper**, and is of no tier, until the person asks for it to be checked. It is shown with its code for them to read.

### Checking it against the paper

What would show that the function does what the paper did is that it gives a number that the paper reports, for inputs that the paper says. Each step of finding that out is held to what a program can check:

- **Which numbers are tried** is not a model's to say. The claims of the paper that are numbers with digits enough to be told from one by chance are tried, at most 10 of them: those that the person gave inputs for first, and then in the order of the paper.
- **The inputs of a claim** are the person's, if they gave some, and otherwise a model's, if the person lets one be asked. The model in the settings is shown the function's signature and docstring, the claim's sentence and number, and the passage of the paper around the sentence (up to 800 characters on each side, cut where a word ends), and may give only values that are written in that passage. A program checks each: a number must be one that the passage has (a percentage is written both as it is and as a part of one, and a number with a sign also without it), words must be in it, whatever their case and spacing, and not as a piece of one of its numbers (85 is not written in 0.85), and a table, true or false, a parameter that the function does not take, or leaving out one that has no default are refused. A parameter that is left out is called with its default. The person's inputs are theirs to say, and are checked against the function alone: its parameters, their types, and how big a call may be. No input, the person's or a model's, may hold the number that is looked for, with either sign, as a function that is given it could give it back.
- **Code that holds the number.** A function whose code has a literal that rounds to the number with either sign, a sum or a product of literals that does, or a text, a docstring, or a comment that has it in it (code can read its own docstrings and its own file) is `hard_coded` for that number: it is not looked for, and no model is asked for its inputs. A number that the code works out from other literals through names or calls is not found this way, which is one reason the code is shown to be read.
- **The calls.** The function is called with the inputs of each claim twice, each time in a process of its own, all in one container of the lab's sandbox image with no network and the ceilings of a tool's calls, and with nothing of the paper's code, as there is none. All of the calls together have the minutes that the person allows, 5 unless they say, and at most 30. The claim's number is then looked for in what the function gave, by the paper's own rounding. It `matched` if it is in one place, and in the same place both times; it is `ambiguous` if it is in two places or more, as which of them the paper means cannot be told, `unstable` if the places are not the same both times, and `not_found` if nothing rounds to it. A call that raised or ran out of time is an `error`, and a claim that was not called for, as the time ran out, is `not_run`. A claim that had no inputs is `no_inputs`, with why: the model found `none_found` in the passage, what was given was `refused` (and why), no model was asked (`not_asked`), the limit was reached (`limit`), the model gave `no_answer`, or the claim has no place in the text (`no_place`).

**What it comes to.** A function that matched at least one number is of **tier C**, and its label says how many of those that were tried it matched, as in "Re-implementation, matched 1 of 3 tried". What was tried is what the function was called for and came back from: matched, not found, ambiguous, unstable, or an error. One that matched none says that it "could not match a number of the paper", with how many were tried, one that was called for none says that it "could not be checked", and one that has not been checked, or whose checking was stopped or failed, is "not checked against the paper". What is kept (`reimplementation/checks.json`) is bound to the hash of the function's code, the paper's file, and the claims that were read of it, so a function that was changed or written again, another file of the paper, or claims that were read again and differ, are of no tier until it is checked again. The person's inputs (`reimplementation/inputs.json`) are bound to the function and to what each claim said when they were given, and go with the function when it is taken away or written again.

What a match shows is that the function gave a number that the paper reports, for inputs that the paper wrote down. The number can still be the same by chance, and it says nothing of what the function gives for other inputs. A function of tier C is still a re-implementation, not the authors' code. It is given to the conversations that are given its agent, labelled as one in its description and in everything it gives (see [Using an agent in a conversation](#using-an-agent-in-a-conversation)), and the page says so too.

**On the page.** The Re-implementation part, after Variants, shows in the order a person goes: why a function cannot be written, if it cannot, as the server says it (the paper is not read, it reports no number with digits enough, the agent has tools of the authors' code, or it was imported, and no form is offered then; a function that was written before and is still kept is still shown), the job while it goes on, what was kept, and the forms. The form that writes lists the sections of the paper with their length and page, those of the method already chosen, and asks for words to look for, a name, and what the person wants of it. What is wrong with those (a name that is not one, words or a wish that are too long, nothing chosen) is said before anything is sent. A button shows what the model would be given, which is the server's `brief` as it would be sent, with which places of the paper it is made of, whether it was cut, and which model. Choosing another section, or other words, makes what was read not what would be sent, and says so and takes the agreement back until it is read again, so that only what was read can be agreed to. When what would be given to begin with is no longer what it was (the paper, the model in the settings, or the agent's title changed), the form starts over with what it is now. The agreement is a box, and the button is not enabled until it is checked; the most that asking the model may spend must be said, and what is wrong with it is said when the button is pressed. Writing again says that it takes away the function that was written, its checks, and the person's inputs. If the server says that what would be sent is not what was shown (409 `changed`), the page shows what it is now, to be read and agreed to again. If it says that the paper is not read, has no number to look for, has tools, was imported, or has no function (422 `no_text`, `no_numbers`, `has_tools`, `imported`, `no_function`), the page looks at the agent again. While the function is written, or checked, the job is followed and may be stopped, the forms and what was kept are not shown, nothing else is done to the agent, and its paper is not read. A writing that is stopped keeps that it was stopped, what it cost, and no function.

What was written is shown as written, failed, or stopped, with how it went in words (the model, how many attempts, what it cost, that it was imported in a container with no network and that nothing else of it was run), the places of the paper it was given, and, for a function, its code to be read, with the words that none of the authors' code is in it. It carries the label "Re-implementation, not the authors' code" wherever the page shows it. A function whose file was changed since, or that was written from another file of the paper than the agent has now, is said not to be used, and is not checked or given to anything. Under it is what came of checking it: its label and tier, each claim with its number and sentence, how it came out in a word and not only by colour, and what that came to in words (whose the inputs were, what the function gave, and where its number was found), and the counts. A claim has a button that shows the passage a model would be shown, and a form for the person's own inputs as JSON, which is held to the function's parameters, as the server holds it, before it is sent; what is wrong with them is said where it is typed, and the server's refusals as it says them. They are counted as the compact JSON that is sent, not as typed. A number with no point is sent as a whole number, so `1.0` is sent as `1`, which a parameter of float takes; a number that is not finite, or a whole number beyond what the page holds exactly (more than 2^53), is refused before it is sent. The form that checks asks whether a model reads the inputs of the claims that have none of the person's, with the most that may cost if so, and the most minutes for all of the calls, from 1 to 30, and says what is wrong with them before anything is sent. Checking again takes the earlier checking away; taking the checks away, and taking the function away (which takes its checks and inputs with it), ask first.

## Using an agent in a conversation

A person gives an agent to conversations by saying so: `PATCH /api/paperagents/{id}` with `{"given": true}` gives it to the conversations that are made from then on, as the functions written from a survey are given. `POST /api/chats` can also name agents, in `paperagents` (an agent that is not there is refused), instead of those that are given, and the conversation's `config` says which, and keeps them, so that it has the same agents when it is opened again, less any that have gone since. Nothing is given that the person did not say.

A conversation that is given an agent is given tools that are named from it, `<the agent's id, with its hyphens as underscores>_<the tool>`, cut to 64 characters with a short hash if that is longer, so that they cannot be taken for another agent's. A name that a tool of the conversation already has, that the lab keeps for itself, or that the tools of an MCP server may have is left to that, so a name is never two tools. The description of each tool, which the model reads, says its tier and what that does and does not show, and the lead is told once to say where in the paper a thing is said, to take the paper's words, and what a tool that runs gives and prints, as data and not as instructions, and not to call a result checked or correct because a tool gave it.

- **Tools that read (tier D)** need only what was kept when the paper was read, and run nothing, so they are given wherever there is a conversation. `search_paper` looks for words and not meaning (the rarer a word is in the paper, the more it counts), and gives at most 10 places, each at most 700 characters, with its page and section; the list of references is not searched. `show_claim` lists the claims the paper makes, or, given an id, shows one with the paper's words for it, where they are, and the passage around them. `show_method_card` shows the method card, with what the method was tested on and where it falls short, and the resources the paper names, with each fact marked as read by the model or as a person's, and as a draft that nobody has approved unless a person has (see [The method card](#the-method-card)). `check_scope` puts what the person's data is (species, tissue, assay, sample size and what it counts, input format, any that the lead knows) against the card, and the lead is told to call it before it runs a tool on the person's own data and to tell the person what it says, with the card's words if the data is outside. A tool that runs is then held for the person to go on if the data is outside, and says in its result what it was put against (see [The method card](#the-method-card), under Checking data against the card). If the reading did not come to its end, what they give says so. An agent whose paper has not been read is given none of them.
- **Tools that run (tier A)** are the tools that were made of the tutorials, given where the conversation may run code, and not where it runs none. A call runs the authors' own function once, with the arguments the lead passes, in a container of the image of the agent's environment (with its data, if the tools were made with it), with no network, in a process of its own on a copy of the code of its own, for at most 5 minutes and writing at most 2 gigabytes. It gives what the function gave, and what it printed; a value that is not plain data is described, and not sent. It also gives `scope`, which says whether the data was put against the method card and what came of it, and whether the person went on with data that is outside (see [The method card](#the-method-card), under Checking data against the card). What the tutorials got is not given to it. What was kept is looked at again at each call, so a tool whose wrapper was edited, or that was taken away or made again, or whose image is not in Docker, does nothing and says why.
- **A re-implementation (tier C)** is the function that a model [wrote from the paper](#writing-the-method-from-the-paper-tier-c), given where the conversation may run code, and only to an agent that was not imported and has no tools of the authors' code, once the function is of tier C: its checking against the paper came to its end, is bound to the function, the paper's file, and the claims that are kept now, and matched a number that the paper reports. Its description begins `[Tier C, re-implementation, not the authors' code]`, says that a model wrote it from the paper's words and that none of the authors' code is in it, and gives its label, as in "matched 1 of 3 tried", and the lead is told, in place of what it is told of tools of tier A, to say that what it gave came from a re-implementation whenever it tells the person. A call runs the function once, with the arguments the lead passes, in a container of its own of the lab's sandbox image (it uses Python's standard library alone), with no network and nothing of this machine but an empty folder, under the same limits as a tool of tier A. What it gives says `label` ("Re-implementation, not the authors' code"), `called`, `tier`, `checked` (its label), `result`, `seconds`, what it printed, and `scope`, and every error that it gives once it is called begins `[Re-implementation, not the authors' code]`, so that what a conversation keeps of it says what it is (arguments that are not JSON, or not a JSON object, are refused before the tool is called, with the error every tool gets for them). It is held for data that is outside the card as a tool of tier A is. What was kept is looked at again at each call, and again once the person has gone on with a call that was held, so a function that was written again, checked again and matched nothing, or whose checks no longer hold, does nothing and says why.

An agent is of the best tier of its tools that run (B if one has passed [checks](#checking-the-tools), otherwise A), of tier C if what runs is a re-implementation, and of tier D if it has only those that read, and each tool says its own, in its description and in `GET /api/paperagents/{id}/given`.

**On the page.** The In conversations part, after Tools, has a box that gives the agent to the conversations that are made from then on (and takes it back), and shows what a conversation would be given of it: the agent's tier, how many tools read the paper and how many run its code, and each tool with its name, what it is passed, what it does, and its tier. A re-implementation is said to be one in its tier (C, "A re-implementation, not the authors' code, which gave a number that the paper reports"), in its label, in what it does, and in a line that says it is said so in all that it gives. If a kind of tool is missing it says why (the paper has not been read, the agent has no code, which for an agent that was made here also says that a function can be written from the paper's words, or no tools have been made), and if the server says the tools that run cannot be called (Docker is not running, or the image is not in it) that is shown as it says it. An agent can be given before it has anything to give. The list of agents marks the agents that are given. The page looks again at what an agent gives when the paper is read or taken away, and when its code, environment, data, tutorials, or tools change. The Tools part of Settings does not list these tools, and says that they are given from the page of the agent.

**How far this has been checked.** What tier D says is that the words are the paper's and where they are, found by their words, so a place that says it in other words may be missed. What tier A says is what it said when the tools were made: the function gave again what the tutorials got, for the arguments the tutorials passed. A call with other arguments is not checked at all. Neither says that what the paper says, or what a tool gives, is right.

### On the team

An agent that a conversation is given is also a scientist of its team, titled `PaperAgent: <its title, cut to 40 characters>` (with the last six characters of its id added if the person's team already has that title, or one that a request to a model would name the same), whom the lead can bring in with `convene_team` or `consult`, as it can the others, and who is then in the team sessions that it brings together, which are given the same tools as the lead (`paperagent_team.py`). Nothing that the paper says is in what the scientist is told, which is a system prompt, where the paper's words would have more say than they have anywhere else: it is told the paper's title, whether all of the paper was read, how many methods, datasets, scope facts, and limitations the card has, and whether the card is a draft or approved, and it is told to speak for the paper and nothing beyond it: to look a thing up with `show_method_card`, `search_paper`, or `show_claim` before it says what the paper says, to give the page and section that they give with the paper's own words, to say that the paper does not say where it does not, and to run the agent's tools when a question needs a result, saying which tier they are of. An agent whose paper has not been read is a scientist who knows the paper by its title only, and says so. The members are made again each time the conversation is opened, so an agent that was deleted since is not one.

With two papers or more, the conversation is also given `compare_papers`, which takes a topic (words) and sets what each paper claims on it side by side, each claim with its page and section, and marks the places where two papers' claims have words in common (at least two, and two-fifths of the words they have) and numbers with none in common as `possible_disagreements`, for the Scientific Critic to read; the Critic is asked, in its role, to use it for the claims that the team relies on from more than one paper and to say where they disagree and what in their data, units, or conditions may be why. A program that matches words and compares numbers has not understood either, so a pair that is marked may not disagree, and one that is not may. It is also given `query_paper_graph`, which says how the papers relate (see [The graph of papers](#the-graph-of-papers)), and, if the agents have tools that run, `check_paper_join`.

**Kinds of files.** A tool of an agent takes names of files and gives values, so whether what one gives can be what another takes is said only in the words of their docstrings. A small layer (`paperagents/datatypes.py`) reads four kinds from those words: an AnnData file (`h5ad`), a `vcf`, a table of `summary_statistics`, and a `table` (a table of summary statistics is a table, and a table is not one). A parameter that takes a file (or a list of them) is declared to take the kinds that its name and the first sentence of its description name, and a tool is declared to give the kinds that the section of its docstring that says what it returns names (in the reST, Google, or NumPy style, and only that section). `GET /api/paperagents/{id}/given` says each tool's `takes` (by parameter) and `gives`. `check_paper_join` says, for a tool that gives and a parameter that takes (or each that takes a file), whether the join `fits`: `true`, `false`, or `null` where either does not say, which is not a yes. When a tool is called, a file name that was passed to a parameter that takes a kind, and that ends as another kind does (`.h5ad`, `.vcf`, `.vcf.gz`, a table's `.csv`, `.tsv`, `.parquet`, and `.gz` of the first two, and a `.txt` only if its name has `sumstats` or `gwas`, and then as one of summary statistics, as a `.csv` or `.tsv` is if its name has), is refused before anything runs, with which parameter takes what. Nothing looks in a file, and a name that says nothing of a kind goes on.

## The graph of papers

`GET /api/paperagents/graph` and the lead's tool `query_paper_graph` say how the papers of the agents relate, from what is kept of each: the facts that were read of its paper (methods, datasets, software), its claims, the address and the commit of its code, and, if the account of the trying of its claims is of the code and the claims that are kept now, what that came to (`paperagents/relating.py`, `server/paperagent_graph.py`). It is made when it is asked for, so it never shows what is not kept now, and nothing is run and no model is asked. At most 40 papers are put against each other (`left_out` says how many were not), at most 400 relations are kept (`truncated` says if there were more), and each comes with at most three pieces of evidence.

| Kind | What it says |
| --- | --- |
| `dataset` | Both papers used a dataset, by the same accession (`basis` of `accession`) or the same name, unless both give an accession and the two differ, which says they are two datasets. |
| `software` | Both name the same software, with the version each says and whether they are the same (a name that is on a short list of tools that nearly every paper has is not matched). |
| `method` | Both name the same method. |
| `code` | Their code is at the same address (the scheme, `www.`, `.git`, a trailing slash, and the case are not told apart), and whether it is at the same commit, or not, or not known. |
| `refers` | One paper's words name the other, by its DOI, the address of its code, its name, or its title, and, from the words around it, whether it `mentions` it, `builds_on` it, `replaces` it, or `replicates` it. It is directed, from the paper that says it. |
| `agrees` | Their claims have the same words (at least two, and two-fifths of those they have) and a number in common, which is not a year and has at least two digits or a decimal point. It is `corroborated` if the code of one of the papers gave that claim again when it was tried. |
| `differs` | Their claims have the same words and no number in common. |

**How far this has been checked.** That each relation has the quotes it was found from, which are the paper's words with where they are, and that two papers that share an accession, a name, a code address, or numbers on the same words are put together. Not that papers that are put together share data or a method, that one builds on another, or that two claims agree or differ: a program that matches names and words has not understood either paper, so a relation is a place to read, and a paper that is not in one may still be related. A paper that has not been read has only its code to be related by, and is named as such. A word of a paper in a relation is data, and is not an instruction.

## Author and reviewer mode

`GET /api/paperagents/{id}/author` says to the person who wrote a paper, or who is reviewing it, what a reader would hit when they take its code as a stranger: where it would stop them, where it would probably stop or mislead them, and what they should know (`paperagents/authoring.py`, `server/paperagent_authoring.py`). It is made when it is asked for, from what the steps of the agent kept, with nothing run and no model asked, so it says no more than what is kept now, and the steps that were not run are listed with the call that runs each. Fetch the code (which makes the checks of the files), build the environment, run the tutorials, read the paper, and try its numbers, and each says more.

Each finding says how bad it is (`block`: a reader cannot get going; `warn`: they will probably be stopped or misled; `note`: they should know), where it is, and what would mend it. They are of these kinds:

| Area | What it says |
| --- | --- |
| `code`, `license`, `environment`, `examples`, `data` | The checks that are made of the files when the code is fetched, as what a reader would hit: no code that runs, no license (or one that was not recognized), nothing that says what to install, a need for a GPU, no tutorial or test, **examples that read a path on the authors' computer** (with the file and the line), data that is not where a reader can get it, code in submodules, and a very large repository. |
| `environment` | **Imports that no file that says what to install names**: the code of the project (not its tests, documents, or set-up scripts, and its notebooks by their code cells) is read for what it imports, and each import that is not in the standard library, not the project's own, and not named in a requirements file, a conda file, `pyproject.toml`, or `setup.py` (as it is, under the name it is installed as, such as `sklearn` for `scikit-learn`, or as a family such as `google` for `google-cloud-storage`) is listed with the files that have it. And **what building it came to**: a build that failed (a stop, with what the output said and what to change), packages that conflict (`pip check`), a project that is not built here, or Docker that was not running. |
| `examples` | A tutorial that does not run to the end in the environment that was built, with no network, and why; one that gives different output when it is run twice; those that were skipped or left out, and a run that did not come to its end. |
| `data` | A dataset that the paper names and that nothing says where to get, and a place for the data that is not one that is fetched from here. |
| `claims` | A number of the paper that the tutorials' output did not give again, or gave in part, when it was tried. |

The `verdict` is the worst that was found: `blocked`, `to_fix`, then `unfinished` (nothing was found in what was looked at, and some steps have not been run) and `ready` (nothing was found and every step was run). A project that has no code fetched is `not_checked`. A project of R or Julia, which is not built here, is said not to have been, and its steps that need a build are not asked for. `ready` says that nothing that was looked at stood in a reader's way, which is not that the code is right or that what the paper reports is.

**The ready package** (`GET /api/paperagents/{id}/author/package`) is a ZIP of one folder, of what the person can put in their repository or send with the paper: `reproducibility_card.md` (the code and its commit and license, the environment and the exact versions and what `pip check` said, how the tutorials ran, what came of each of the paper's numbers, where the data is, the tools and their tiers, and what a reader would hit, each with how far it was looked at), `availability_statement.md` (a short statement of where the code, the data, and the software are, in which what is not known is a `[bracket]` for the authors to fill and is not made up), `findings.json`, the exact versions of the environment that was built (`requirements.lock.txt`, or `environment.lock.txt` for conda, without the project itself), and, if a package of the tools was made and is of what is kept now (see [The lab's library](#the-labs-library-and-exporting-tools)) and is no more than 20 megabytes, that package under `mcp/`. The card and the statement are also in the view, so that they can be read before they are saved.

**How far this has been checked.** That each finding comes from a file, a step's record, or the paper's own words, which it names; that the imports are of the code as it is parsed, not run; and that what the paper says is shown as one line of text that cannot break a table. Not that a finding is a fault: an import is looked for by name, so one that is installed under a name that is not known, or that is only tried, is a false alarm, and a thing that is not in a file that was looked at is not found. Not that the package is right: the card says what was found and the statement says what is known, and a person is to read them before they go in a paper.

## Triage of a listing

A listing of preprints is long, and most of its papers have no code that tools could be made from. `POST /api/paperagents/triage` puts them in the order that they are worth going on with, before any is built, from what a look at their code says (`paperagents/triaging.py`, `server/paperagent_triage.py`). The papers are those that a person gives by DOI (with the address of their code, if they know it), or those that bioRxiv lists for a period and a subject, or both. It is one job at a time, which can be stopped (`POST /api/setup/jobs/{id}/stop`), and what was looked at before it was stopped is kept; a triage is kept in `triages/` in the workspace, as a file of its own, and no more than 20 are kept.

For each paper the address of its code is the one that was given, or else **the first address in its abstract** that is of a project at one of the four hosts of code (GitHub, GitLab, Bitbucket, and Codeberg; a host that is the end of another word or address, such as `notgithub.com/...` or `evil.example/github.com/...`, is not one), with the others that the abstract gives said beside it. A paper that was given by DOI alone has its abstract looked up in Europe PMC (for at most 30 papers of a triage). The code is fetched at the default branch, at one commit, with none of it run, taken stock of, and put to the same pre-flight that an agent's is, and then taken away again; no model is asked and no PaperAgent is made. A paper that is worth going on with is made into one by the person, with the address that the triage found.

The order is by the answer of the pre-flight (`go`, then `ask`, then `no-go`), and, among those that have the same, by the fewest blocks, warnings, and checks that did not know, the most tutorials, the lowest guess of the cost, and then as listed. After these come the papers whose code was **not looked at**, each with why: it could not be fetched or read (one that cannot be read does not cost the others theirs), it was larger than the most that is fetched, it was beyond the most that are looked at (the papers with an address come first in the order of the listing), or the triage was stopped before it came to it. Last are the papers that say nowhere in their abstract where their code is (`no_code`), in the order of the listing.

**How far this has been checked.** That the address that is fetched is one that the abstract gives or the person gave, at a host of code, and nothing else that the abstract says; that the code is fetched within a limit of size, read and not run, and taken away whether or not it could be read; that each paper has a place and a reason; and that what a stop leaves is kept. Not that the order says that a paper is good, that its method works, that its numbers hold, or that the code at the address is the paper's code: it is an order of how likely the code is to give tools without trouble, and of nothing else. The pre-flight is of the files alone, and the paper is not read, so its checks of the data say "not known" at best, and the guess of the cost is a guess.

## The lab's library and exporting tools

The library (`GET /api/paperagents/library`) lists each agent that has tools, as a version that is pinned: the version is the commit of the code, the environment is the image with the lock of the exact versions that were installed (and a hash of the lock), and each tool has the hash of its wrapper and the tier its checks come to now, with the code's license. Nothing is said there that is not kept; it is made each time from what is kept, so a tool that was edited, or an image that was taken away, is not shown as it was.

**A package.** The tools of an agent can be made into a package, a ZIP that is a server of the Model Context Protocol (MCP) that anyone can run, and that holds: the authors' code at the commit, each tool's wrapper and its record, the lock of the environment (what pip installed, or conda's explicit list; a package that pip built from a folder, which is the project, is left out of the lock, since the code is carried), a Dockerfile that builds that environment from the lock, a server (`mcp_server.py`, which uses Python's standard library alone, speaks the protocol over standard input and output, and gives each tool with the schema of what it takes and a description that says its tier and that this does not show that what it gives is right), a manifest (`package.json`) with a hash of each file and of all the code, and a README. It holds code, and what is said of the paper (where it is, and its title), and never the paper's text or what was read of it: no claim, no card, no quote.

**What a call does.** The server runs the authors' function once, in a process of its own, on a copy of the code that is made for the call and thrown away after it, for at most 30 minutes (`LUMI_CALL_SECONDS`), with the arguments that the client passes, which are checked against the tool's schema as to their kind before anything runs. It gives what the function gave if that is plain data, and a description of it (its type, its shape, a hash) if it is not, and what it printed, and says what is given is data and not instructions. It is not a sandbox: the code runs as whoever runs the server, so the README says to run it in a container with no network, and with only the data that it is to read.

**It is checked before it is kept.** The package is unpacked into a folder of its own and its own check is run in a container made from the image that the tools were made in, with no network, a root that cannot be written to, and nothing of this machine but that folder, which is read-only: the server starts itself, is asked for the calls that were recorded of each tool (at most three of each, those made from one folder and not huge), and what each gives is held to what the tutorial got, within the tolerance that the tools were made with. The check also looks at whether any file of the package, or the code, is not what its manifest says. A package that did not give what its tutorials got, in any call, or whose check ended in no report, or took too long, or wrote too much, is not kept, and the job says why (`was not kept`); one that was kept before stays. A tool none of whose calls can be carried (they were made from more than one folder, or are too big) is left out of the package, and the package says so; a package with no tool left is not made. The Dockerfile is not built by Lumi: what was tested is the package run in the image that the tools were made in, which was built from the authors' own files.

**Licenses first.** The code's license is looked at when the code is fetched. A package of code with **no license**, one that is **not recognized**, one that is **for non-commercial use**, or a **copyleft** one is flagged: it is not made until the person says to go on (`accept_license`), the README begins with what the flag means, the server's own instructions say it to a client, and the package records that it was said. A license that is not flagged (permissive, public domain) needs nothing said. What the licenses of the locked packages are was not looked at, which the README says. The flag is not legal advice; it is what the license text was found to be.

**Stale.** A package is kept with what it was made of (the commit, the image, the license flag, each tool's wrapper hash and its tier and the kinds of check that passed), and is shown as not `current`, and cannot be downloaded, once any of these is not what is kept now, such as when the tools are made again or checked. Taking the tools, the tutorials, the environment, or the code away takes the package too, and so does `DELETE /api/paperagents/{id}/export`. While a package is made nothing that changes what it is made of is done to the agent (409 `busy`), and the job can be stopped, which keeps no package.

**How far this has been checked.** That the package, run in a container as it is run elsewhere, gives again what the tutorials got for the calls that were recorded. Not that what a tool gives is right, that it works with arguments other than the tutorials', that the Dockerfile builds (it was not built here), or that the code may be given to others on the terms of its license, which only the license's own text says.

## Living agents

An agent is one commit of the authors' code and an environment that was built from it, and both go out of date. A person who comes back to an agent in a few months is told how it is. A look at an agent (`POST /api/paperagents/{id}/health`, a job that can be stopped, or on a schedule) does four things and changes nothing that is kept:

- **Where the code is now.** The code's address is asked, with `git ls-remote`, for the commit that the ref it was fetched at is at now, and nothing is fetched to ask. The ref is where it was (`same`), has moved (`moved`), or is not there any more or its project is not (`gone`); if it could not be asked, that is said (`unknown`), and a commit that was fetched by its hash does not move (`pinned`).
- **A newer version, as a diff.** If the ref has moved, the newer commit is fetched into a folder of its own and put against the code that is kept: each file that changed, was added, or was removed, with a bounded diff of text (the lines of the first 40 files that changed are compared and shown; a file over 512 KB, one with too many lines to compare, a binary file, and a long diff are said to be cut and not shown whole, and the lines added and taken away are not counted of a changed file that is not shown), which of the tools are of a file that changed (matched by the file of the module that holds each tool's function, so a tool that calls another file is not told of by it), and which files that say what an environment is made of (a requirements file, `environment.yml`, `pyproject.toml`, `setup.py`, and the like) changed. It is kept as a proposal, for the commit that is kept now.
- **The versions that are pinned.** Each version that a pip lock pins is asked of PyPI (one host, one kind of address, no redirect followed, at most 150 of them and 90 seconds), and a version that is gone or was yanked is what a build of the lock would fail on, or be warned of. A version that PyPI did not say of is counted and is not held against the agent; a local version (`2.1.0+cu118`) is not asked of, as it is of a build that PyPI does not have.
- **The tools, run again.** Each tool's recorded calls (at most three of each, as a package's check makes) are run again in the environment that is kept, in a clean container with no network, and what each gives is held to what its tutorial got, as a package's own check does it (see [the lab's library](#the-labs-library-and-exporting-tools)). It is the same check, so a look is a package that is made, run, and thrown away, and no package is kept.

**What the words mean.** *Healthy*: the tools gave again what their tutorials got, and nothing that was looked at is gone. *Degraded*: something is wrong and the tools may still be used: one gave something else (the tools that did not and the first thing that differed are said), a pinned version cannot be had, or the code's source is gone. *Broken*: the tools cannot be used as they are: the image of the environment is not in Docker, or no tool that has a recorded call gave again what its tutorial got. *Unchecked*: nothing wrong was found, but the tools were not run (Docker was not running, the agent has no recorded call to hold a tool to, or the package's own check could not run or gave no report), so it is not known that they work. Docker that did not answer about the image is not the image being gone. A tool with no recorded call is not held to anything and is left out of what is said. **A newer version of the code is not one of the words:** the version that is kept still works as it did, and a newer one is shown beside the word (`update`), with its diff.

**It is a record of one look.** What a look found is kept with the commit, the image, and the tools it was of (`living/health.json`), and is not shown for others, so an agent whose code, environment, or tools were made again is unchecked until it is looked at. The last ten words are kept as its history. Taking the environment away takes what was found, and taking the code away takes a proposal. The agent's entry in the library has `health`: the word, when it was looked at, whether a newer version is proposed, and the hours it is watched at.

**Pinned until the person says.** The commit, the environment, and the tools stay as they are, however many newer commits there are, until the person approves one: they read the diff (`GET .../update`) and send the full commit that they read (`POST .../update/apply`), which is refused if it is not the one that is proposed (a proposal that was replaced by a newer one since, or put aside, is not what they approved). It then fetches the code at that commit, as the fetching of code does, and what was made from the old commit (the image, the tutorials' run, the tools, the checks, the package) is taken away as it is whenever the code changes, and is made again by the steps that made it, which the person starts. Nothing is repaired by this program: it shows the diff and takes the commit; it does not edit code, and that the newer commit works is not said until the tools are made and checked again. Putting the proposal aside (`DELETE .../update`) keeps the version that is kept, and the proposal comes again at the next look if the code has moved.

**On a schedule.** `PUT .../watch` with `every_hours` has the agent looked at when the server checks the schedules, which it does once a minute while it runs: an agent is looked at if it was never started since the schedule was set, or that many hours have passed since a look was last started. An agent that has something else done to it at that time is left and is looked at at the next check, and a look that is refused does not use up the hours. Nothing is looked at while the server is not running, and a missed hour is not made up for: the next check looks once. The schedule is the person's and stays when the code is replaced.

**How far this has been checked.** That the tools, in the environment that was built, gave again what the tutorials got, the day it was looked at; that a pinned version was on PyPI that day; that the code's source answered as it did. Not that what a tool gives is right, that a newer commit is better or breaks nothing (only the tools' recorded calls can be run again, and only in the image that is kept), or that an environment that is built again from its files would build.

## Importing an agent that someone else made

An agent can be made elsewhere and brought in, instead of being made here. The first kind that can be is a server that someone hosts: Paper2Agent hosts three, for Scanpy, TISSUE, and AlphaGenome, and any other MCP server at a web address can be imported as well. An imported agent is an agent of its paper, as any is, with an `imported` block that says where its server is reached, who made it as far as is known (`origin`, which is `Paper2Agent` only for those three addresses, since the name of a host does not show who made what it holds), when it was imported and last connected to, and the tools it listed, each with its name on the server, what it is for in a line, and the names of its arguments. The address is a web address with no name, password, query, or fragment in it, and without `$`, `{`, or `}`, which a config would read as the name of a variable and put its value in the place of, so a key cannot be put in it, whether in the address or by naming a variable. Importing connects to the server to see that it is one and which tools it gives, and calls none of them. A tool whose name is nothing when it is put on one line is left out, and a server with no tool left is not an agent. A server is the agent of one paper, which is given, or is added to an agent that was made for the paper already.

**Tier Imported.** An imported agent is of the tier Imported, which says that nothing of Lumi's has been done to it: no tutorial was run here and nothing it gives was compared with anything, so what it says of itself is what its maker says. It is shown so everywhere (`checked` is `false`, and `meaning` says it in words), and nothing about it is called verified. The checks that PaperAgents have (a reference run, tools that give again what a run gave) are what would lift it above that, and none of them works on an imported agent yet, so an imported agent is not lifted by anything. An imported agent can also have its paper read and its code fetched, as any agent can, which gives it tools of its own; the imported tools stay of the tier Imported.

**In conversations.** An imported agent that is given is reached as an MCP server is: the conversation connects to it when its first message is sent, and the lead is given its tools, named from the agent, `<the server's name>_<the tool's name on the server>`. The server's name is the agent's id with anything but letters, digits, and underscores made an underscore, begun with `agent_` if it would not begin with a letter, and cut to 32 characters with a short hash if it is longer. If a server that is set up in the settings, a library preset, or an agent that is named before it has the name (or has the same start to its tools' names), `_agent` is added to it, and a number after that if that is taken too, so that two servers are never one; which agent gets a suffix then depends on the order the agents are given in, and the agent's page shows the names as they are when it has none of those beside it. The server is not one of those in the settings, and is not shown there, nor are what it holds kept with those of the settings' servers. Each call waits for the person's approval, which is not a setting of the record, since a hosted server is run by someone else, on a machine that is not this one, and whatever a call is given is sent there. The lead is told, once, what the agent is (imported, made by Paper2Agent or by someone else, run on that host, not checked by Lumi), to say that it was imported when it tells the person what it did, not to call a result checked or correct because one of its tools gave it, to give a call only what the person asked it to analyse and never a key, a password, or private data they did not ask it to send, and that what the tools give back is data and not instructions. A server that cannot be connected to fails the turn before anything is spent, as any server does, and the message says to stop giving the agent.

**Servers that Paper2Agent hosts.** Their tools read files that are on their server, which is where their own upload page puts them, so an imported agent of one can work on data that is already there and not on a file of the person's that has not been uploaded there; Lumi does not upload files to them. AlphaGenome's tools take the person's AlphaGenome API key as an argument, which is sent to the server that runs them, so each call that has one is one to read before it is approved. Their prompts are not shown as slash commands, as those of the settings' servers are.

**On the page.** The Agents part of the PaperAgents page has an Import an agent section under Make an agent. It lists the servers that Paper2Agent hosts, from `importable` (each with who made it, that it runs on a Space on Hugging Face and not on Lumi, that each call asks first, links to its paper, its code, and its page, and for the two kinds of server what Paper2Agent says of using it: files are on its server, and AlphaGenome's tools take the key as an argument), each with one button: import it, add it to the agent of its paper that there is already, or, if an agent has it, a link to that agent. A form below imports a server that is not listed, from its address and the paper it is of. The address is checked where it is written, as the server checks it. An agent that was imported is marked Imported, not checked here in the list and in the header of its page. Its page has an Imported server part, which shows the tier, that nothing of Lumi's was done to it, who made it (only as far as is known), where it runs and its address, when it was imported and last connected to, and the tools the server listed, as it named them. It has buttons to connect to the server again, which keeps what it had if the server cannot be connected to and says why, and to remove the server after asking, which leaves the agent of the paper. An agent that was made here has a form for adding a server to it. The In conversations part shows the tier Imported, the imported tools as a conversation would call them, each said to call a server that someone else runs and to ask first, and what the tier means. The Tools page does not list these agents among the servers, and says where they are imported.

## Bake-offs

A person often does not need the method of one paper. They need a method for a task, and several papers claim to have one. **A bake-off** is that question: what the person wants done, which of their own data (from the Data page) it is to be done on, the methods that are in the running, and one limit on what the whole of it may spend. It is kept in `bakeoffs/<id>/bakeoff.json` in the workspace, and not in any PaperAgent's directory, since it is of many papers and an agent is of one. A method that is built later becomes a PaperAgent of its paper like any other, and the bake-off says which by the paper, which is what an agent is told from others by, and keeps nothing of it, so that an agent that was made, changed, or taken away since is as it is now and not as the bake-off last saw it. So far it finds the methods, builds them, says whether the data is within what each method's paper covers, and runs a tool of each on the data, as the person says, and keeps what came of it, and puts the methods side by side: how each came out, what it cost, and whether they agree. It can be told where the right answers are, and then scores the methods by them and ranks them by that. The page has a part for the bake-offs (`/papers?view=bakeoffs`, and one is `/papers?bakeoff=<id>`) where one is made, changed, and deleted: what is wanted, the data, what it is, where the right answers are, and the limit. A bake-off's own page also has its methods: they are found in the literature (with searches that the person may say, and the model's own words for why each was chosen, which are shown as its reading of abstracts and not a ranking), added by DOI or link, renamed, given their code, removed, and built, one or all, with where each stands and why, the addresses that a paper points to offered as code only for the person to say so, what the data is against each method's card, and the person's going on with a method whose card the data is outside of, which they can take back. What is being done is shown with the way to stop it. The page also runs the methods and puts them side by side. Under Run the methods, each method that is built has a box to run it, and the call is the person's (a tool of its agent, with its signature shown, and its arguments typed as a JSON object, which is checked where it is written as the server checks it, so that a number such as 3.0 is to be written 3) or a model's, which the page says is the settings' model and that it sees the data's place and not what is in it; the most minutes one call may take is said (1 to 30), the one limit that the run spends from is said, and what is being done is shown with the way to stop it. What came of the last run of each method is shown: whether it ran and why not if it did not, who chose the call, the tool and its tier, what the data was and that it is told by names, sizes, and times, what it was told of the method's scope when it ran, how long it took, the arguments, what it printed, the start of what it gave, and, on asking, the whole of what was kept of it; it says that this is what ran and gave and not that it is right, and warns when the data is not as it was when the method ran or the method was built again since. Under How they compare, a table has a row for each method (how it came out, the tool called, how long it took, what reading its paper cost and what asking a model for the call cost, who chose the call, what was kept of its answer, and how it stands against the other methods, which is unknown where what was kept does not show it), and another has each two of them, with how closely numbers must agree, which the person may change (and go back from) and which is said back. If the person has said where the right answers are, the table also gives each method's score and rank, and a method with none is shown as not scored and not as scored zero; if not, it says that there are no right answers and that the methods are compared only with each other. It says what agreeing means (that it is not being right), and both tables can be downloaded as CSV, made with the tolerance that is asked for.

- **The limit.** It is always said when the bake-off is made, and may be raised, and is never less than what has been spent. Every step of a bake-off that asks a model is given what is left of it, and what the step used is added when it ends, whether it came to its end or was stopped or failed, so that it is one limit for all of them, and for all of the time, and is not set again by each step or each time that the bake-off is carried on. As in the reading, no request is begun once the limit has been reached, so the last one may go over it. A response that does not say what it used makes what has been spent not known, which is kept (`cost_known` is `false`), and no model is asked after it for that bake-off, since a limit cannot be kept without it.
- **Finding methods.** A model is told the task, and what the person says of their data, and writes up to three short searches, or the person gives them (`queries`), which are made plain: operators and the syntax of the services are taken out, so that no search is a command to them. A program runs each in Europe PMC (with abstracts) and on arXiv, and takes from each search and service in turn, so that none fills the list, each paper once however many searches and services found it, up to 30. A service that cannot be reached is said, and what the other gave is used; if none can be, the job fails and says why. The model is then shown the task and the abstracts, between tags that nothing in them can close, and chooses, by their numbers, up to 8 of the papers that are of a method that does the task, each with the words of its abstract that it went by. A program checks that those words (30 to 400 characters) are in the abstract, as whole words of the abstract, allowing only for spacing, curly quotes and dashes, and the form a letter is written in, and what is kept is the abstract's own text; a choice of a paper that was not shown, a paper chosen twice, or words that are not in the abstract is thrown away, and counted in `shortlist.dropped`, so that a model that makes up what an abstract says is seen to have.
- **What a candidate found this way is.** It is a model's reading of abstracts, and is shown as that (`meaning` says it in words). It is not said that the method works, that it works on the person's data, or that it is the best of those there are, and its place in the list is not a ranking. Europe PMC papers are kept as DOIs, which can be read later only if they are open access (`found.full_text` says); arXiv papers are kept as the link to the PDF.
- **Code is only a suggestion.** The addresses of code that an abstract has in it, at the hosts that hold code, are in `suggested`. A candidate's `repo` is empty until the person says where its code is, and nothing is fetched from a suggestion, nor from anywhere else, before they do.
- **What the person can do.** Add a method that the search left out, by its DOI or a link to its paper (one method for one paper, at most 12 in a bake-off, and at most 50 bake-offs), name it, say where its code is, take it away, and find methods again, which adds what is new and takes none away, including what the person added, and counts as `already` what is in the running. While methods are being found, built, or run, the bake-off's title, task, data, and limit, its deletion, and another finding, building, or running are refused (409 `busy`); methods can still be added, named, or taken out, and what the finding adds is added around them. A job that is stopped keeps what was spent and none of what it found.
- **Building the methods.** Only the methods that the person asks for, or that are not built, are built, as one job, one after another, whatever came of the one before. Each is given the PaperAgent of its paper, which is the one there is, or one that is made and named as the method is, and then has done to it the steps that a PaperAgent has, each started as its page would start it and waited for, so that what is built is what anyone could have built by hand and can be looked at, and carried on, on the PaperAgent's page, and a step that was done by hand is not done again. The order is the one that costs least: where the code is and fetching it; looking at it, which acts on a no-go only, so that a method that cannot be used is not paid for before its paper is read; reading the paper; looking at the code again with what the paper says of its license and data; the environment; the tutorials; and the tools. A method is **built** when its PaperAgent's tools are made, and from the code that the bake-off says it has: a PaperAgent that was built from other code than is now said is not that method, and building asks which. Nothing is told that a step is done: what each came to is asked of the PaperAgent.
- **What stands in the way of a method** is one of four, said in words with the step it was at, and kept with the method (`build`; what is seen of where it stands is made from the PaperAgent each time, so that one that was built by hand, or whose environment was taken away, is as it is). `waiting`: it is for the person to say. Where the code is, when none was given (`no_code`, or `choose_code`, which lists what the paper points to and what its abstract does, and none of which is its code until the person says so); which of two addresses is, when its PaperAgent has its code at another than the bake-off says (`code_differs`); and whether to go on, when looking at the code found things to weigh (`ask`, with what they are), which the person says in `go_on`, and is kept with the commit of the code that it was said of, and is not said of another. `blocked`: it is so of the method and nobody can change it here, as when looking at the code says no-go, the environment is of a kind that is not built here, there is no tutorial to make tools from, none of the calls that the tutorials made came to a tool, or its PaperAgent is imported from a server that someone else runs. `failed`: a step went wrong, which may not the next time it is asked for. `pending`: it was not got to, because the limit was reached or building was stopped.
- **What it costs.** Only reading a paper asks a model, and it is paid for out of what is left of the bake-off's one limit: it is given what is left as the most it may spend, and what it spent is found in what it kept, chunk by chunk, and added whether it came to its end or not. A paper read in part when the limit is reached leaves the method `pending` (`limit`), and building again after the limit is raised reads only the chunks that were not. A paper that was read already, by hand or before, is not read or paid for again. A chunk that does not say what it used makes what has been spent not known, as it does for finding. The other steps ask no model, and the estimate that looking at the code makes of making tools is of nothing that this spends. As in the reading, the last request of a reading may go over the limit.
- **Stopping.** Stopping the job stops the step that is going, keeps what was built and read, and leaves the method it was at `pending` (`stopped`), and those after it as they were. Building again carries on from there, and fetches, reads, and builds nothing that is done. A step that someone else stopped, on the PaperAgent's page, leaves the method `pending` and goes on to the next; a step that someone else started on the PaperAgent is waited for, and not done twice.
- **What the data is.** The person says it (`described`), in the words that a PaperAgent's scope check takes: its species, tissue, assay, input format, and how many samples, counting what. It is theirs to say because only they, or the data's own description, know it, and a fact about the data that a model wrote would be a model's say-so in the place that decides whether to warn. Nothing is made of the Data page's description by a model. What is left out, or is only space, or is a size of none, is not said; a word that is not one of those, or that has a control character in it, is 422 `invalid`.
- **Scope of the method.** Once a method's paper is read, a program puts what was said of the data against the method card (see [scope](#the-method-card)), for each method by its own card, as it is **now**: inside, outside, or not covered. It is not kept, since the card may be changed, approved, or made again, and the data said again, and an answer that was kept would say what is no longer so. If nothing has been said of the data, the method has no PaperAgent, or the paper is not read yet, it says that it was not put against a card, and why. Inside is not that the method works on the data, and outside is not that it fails on it; a card that does not say is `not covered`, which is shown and not taken for either.
- **Going on with a method that the data is outside of.** It is a warning and not a refusal. A method whose card the data is outside of is not to be run on it until the person says to go on with that method, which they say of what they were shown (`key`, made of the data as it was said and the card's words it was outside of), and which is kept with that key. It is not going on with the data said otherwise, or with a card that says something else now: the key then differs, the method shows as outside again, and they are asked again. The key is of the words that they saw and not of the PaperAgent or the state of its card, so a PaperAgent that is made again, or a card that is approved, with the same words, is the same going on, as nothing that the person saw has changed. It is only that method's, and may be taken back.
- **Running the methods.** The methods that the person names are run as one job, one after another, whatever came of the one before. The call is the person's: for each, which of its tools and with what arguments. Or it is a model's, if the person asks for one to be proposed (`propose`): the model in the settings is told the task, what the person says their data is, where the data is (`/data/<name>`, and whether it is a file or a folder, but not what is in it, nor the names of files in a folder), and, of each of the method's first 15 tools, its name, the function that it calls, what the code says of it, its parameters (and which have a default), and up to two of the calls that the tutorials made of it (cut at 300 characters, and said to be on the tutorials' own data). It gives one tool's name, the arguments as a JSON object, and a sentence of why, or no tool and why. That is data and nothing more, and what a program checks of it is what follows, as for the person's, whoever chose the call. The model is asked last, once nothing else stands in the way of the method (the data is there, it is not outside its card or the person has gone on with it, it is built, and its tools can be run), so that nothing is spent on a call that would not be made, one request per method, and none is made again if what the model gave is refused. It is paid for out of the bake-off's one limit, as the reading and the finding are: no request is begun once the limit has been reached, so the last may go over it, and what was used is added when the job ends, whether it came to its end or was stopped or failed. A method whose call was still to be proposed when the limit was reached is not run, and says so (`limit`). Besides what follows, the tool that a model chose has to be one of those that it was shown (`no_tool` otherwise), and some argument has to be the place of the data or a place under it, since a call that does not use the data is not a call on it (`bad_call`). A model that gives no tool is `not_proposed`, with its reason. What a model said is kept as its words: it cannot say that its choice is right for the task, or that what the tool gives is right, and nothing it says changes what the tool gives. A program checks it before anything is sent: the tool is one that the method has now; the arguments are an object of plain JSON by the names of the tool's parameters, each of the type that the tool's signature says, with every one that has no default given and none that the tool does not take; and any text in them that starts with `/data` (looked for in what is nested up to 20 levels deep, and in whole strings only, not in the middle of a longer one) is a place in this bake-off's data, which is `/data/<name>` and what is under it (not out of it with `..`), and is there. This check is to say what is wrong before a container is started, and it is not what keeps other data out of reach: the container is given only that one piece of data, so a place of any other is not there to be read. The tool is then called once, as a conversation's call of a tool is: in a container of its own from the image of the method's environment, with no network, on a copy of the code of its own, for the minutes that were allowed and writing no more than is allowed. The person's data is given to it to read, and only that: read-only, at `/data/<name>`, where the lead is given it. Nothing of the person's else is given, and nothing that a call writes is kept. Stopping the job stops the call that is going and keeps what was run before it; Docker not running a call ends the job and says so, since it is not a failing of the method.
- **A method that is not run is shown, with why.** It is kept as a run is, and not left out: `outside`, when the data is outside what the card of its paper says and the person has not gone on with that method (the tool is not called, and the reason says what the card warned of); `not_built`, when it is not built, or its tools or the image of its environment are gone; `no_tool`, when it has no tool of the name (or, of a call that a model proposed, none of those that it was shown); `bad_call`, when the call is not as the tool's signature says, with each thing that is wrong (or the arguments that a model wrote are not JSON of the kind that is allowed, or none of them is the data); `not_proposed`, when a model was asked and chose no tool, and `limit`, when no more was left of the limit to ask it with, which only come of a call that a model was to propose; `data_missing` and `cannot_mount`, when the data is gone, or could not be given to the container. Data that was never put against a card, because nothing was said of it or the paper is not read, is run on, and the run says that it was not. Where no data is named, or it is gone from the Data page, nothing is started at all.
- **Where the right answers are.** The person may say that a table of theirs on the Data page has them (`labels`): the file, the column that has the answer for each row, and, if the rows are not in the order of the data, a different column that says what each row is the answer to. What is kept in the bake-off is those names, and nothing of the file: it stays where the Data page has it and is read from there each time, so the answers are what it has now, and it is not given to any method, which is run on the data of the bake-off only (unless the person named the same file as the data, or the data is a folder that has it, which `in_data` and `says` then say, since a method is then able to read the answers). The file is a `.csv` or `.tsv` (it is not sniffed), at most 16 MiB, and its first line is read, as far as 256 KiB, to see that the columns are there, as they are written without the space round them; a name that two columns have is not taken, as it would be a guess, and the two columns are not the same one. Saying part of it (a file and no column), a file that is not on the Data page or is not there, is a folder, or is another kind of file, or a column that is not in it, is 422 (`unknown_data`, `missing_data`, or `invalid`), with the columns that the file has. A bake-off whose file has changed since, or gone, is shown as it is (`ok` false, and why) and is not refused. That the answers are right is the person's word, and nothing here checks it. How the methods are held to them is under **Scoring**.
- **What a run says.** The latest run of a method is kept in `bakeoffs/<id>/runs/<method>.json`, and not in the bake-off's file, as a result may be big. `ran`: the call came to an answer, kept with the `result` as the tool gave it (the value if it is plain data, and what it is if not), what it printed, and the seconds that it said it took. `failed`: it was made and did not come to an answer, with why: the authors' function raised (`error`), it ran out of time (`timed_out`) or wrote too much (`too_big`), or the container ended without saying how it went, or in a way that cannot be kept (`no_answer`). `not_run`: as above. Each says what ran and on what: the tool, with the function that it calls and its tier; the arguments, and whose they were (`by`: `person`, or `model`, and then `proposed` says which model, the tool and the arguments as it said them, its words for why, and what asking it cost, which are its words and not findings); the method's PaperAgent and the commit and image that its tools were made of; the data as it was listed (its name, where the container had it, how many files, how many bytes, and a fingerprint of their names, sizes, and times of change, which is not a hash of what is in them), and what it was put against the card with. What a call gave is kept as far as it was given room for: 400,000 characters, which is ten times what the calls of a tutorial are kept to, so that a list of some thousands of labels, or an array or a table of that many values, is kept whole and can be compared with what another method gave or with labels, and not as a hash and a look at it, which cannot be (a list or a value that is more than the room, or an array or a table of more than 50,000 cells, which is as many as the room has room for at 8 characters a cell, is kept as a look, and values are not kept if they do not fit). A result that is more than can be kept (the file is 1 MiB at most, which a result that is nested deeply reaches before the room is used) is described, with its type, how long it is as JSON, and a hash of it, so that two can still be told to be the same, and the method still ran. A page is shown the start of a result, and asks for the rest. `since` says which of `data` and `method` are not as they were when it ran: the data if what it is listed as now differs, or it is gone, or the bake-off is of other data; the method if its PaperAgent was built again, from other code, or is gone. A run does not say that what a method gave is right: it says that this call was made to this code on this data, and what it gave.
- **Side by side.** `GET /api/bakeoffs/{id}/comparison` and its tables (`methods`, `pairs`) are made each time from what is kept, with nothing run and no model asked. Every method is a row, whichever way it came out: a method that cannot be built says why (`not_built`, with the reason that building was stopped for), one that was not run says why (`outside` the card of its paper and not gone on with, no tool, a call that was not as the tool's signature says, and so on, or `not_yet` if it is built and was not run), and one that failed says how. The tier is the tier of the tool that was run: A means that the tool gave again what the paper's tutorial gave, which is not a finding about the method on the person's data. Cost is kept in two: reading the method's paper, which is what its PaperAgent's reading cost (and may have been paid before this bake-off was made), and asking a model to propose the call, which is what the run says it cost (nothing if the person made the call); neither says that the other was spent. Two methods agree if what was kept of what they gave shows that it is the same answer: numbers within the tolerance (a whole number and a number that is not whole are both numbers; two whole numbers must be equal), lists of the same length item by item, objects by key, text exactly, and arrays or tables by shape and values. It is not said that they agree, or that they differ, where what was kept does not say: an answer that was kept whole against one kept only as a look at it, results that are not the same kind, arrays of which only hashes were kept and the hashes are not the same (a hash says whether two are exactly alike and not how close), or an answer that was more than could be kept and is only a hash. That is `unknown`, with why. Two runs that were made on the data as it was listed at different times (only the latest run of each is kept, so a method may have been run after the data changed) are not compared, and say so. Methods that agree are not shown to be right, since they may be wrong in the same way, and a method that differs from the rest may be the right one: there is no ranking, and none is made without an answer that is known to be right, which is the person's to give (see **Scoring**).
- **Scoring.** If the person said where the right answers are, each method is held to them each time the comparison is made, from the file as it is then, read whole as text (a cell is what is written in it, without the space round it; an empty cell is a row that has no answer, which is not an answer of nothing; a line with nothing in it is not a row; at most 200,000 rows, since an answer that was kept whole is at most 400,000 characters). The score is **how many labels a method matched, out of how many labels there are**: the labels are the rows that have an answer, the same number for every method, so a method that gave fewer items is held to the same number as the others and loses for it. What a method gave is matched to the rows in one of two ways, by what it is. A *list* has an item for each row of the file in its order, and has to be as long as the file has rows (a longer or shorter list cannot be told which item is of which row, and is not scored, rather than scored as wrong). An *object* has an item for what each row is the answer to, which is its key, and needs the column that says that (`id_column`): an item that is not given for a row that has an answer is wrong and is counted as `missing`; a key that is no row's is counted as `extra` and is neither rewarded nor penalised; a name that two rows with answers have, a row with an answer and no name, or no key that is in the file at all is not guessed at and the method is not scored. An item matches a label if it is the same text exactly (not another case, not other space), the same number within the tolerance of the comparison (a label is a number only if it is written plainly, as `5`, `-0.5`, or `1e3`; `nan`, `inf`, `0x10`, `1,5`, and words are not numbers), or the same truth (`true` or `false`, in any case, is held to a true or false item, and a number is not a truth). Only an answer that was kept whole, or a look with all the values of a list or an array of one dimension, is held to the labels: a table, an array of more dimensions, a look at part of an answer, and a hash are not scored (`not_kept`, with why), and neither is a method that gave no answer (it failed, was not run, or was not built: `no_answer`), or whose run is of the data as it was listed at another time (`data_changed`, since the labels may be of other rows), or when the labels cannot be used now (`labels_unusable`: the file is gone, changed so a column is not in it, has no answer in it, or more rows than can be held; the comparison then says so, and nothing is ranked). A method that was not scored is not the same as one that matched none: it has no score and no rank. **Only the methods that were scored are ranked**, by the number matched; those that matched the same number share a rank, and the next rank is the one after them all (1, 1, 3). A score says how often a method gave the same answer as the person's labels and nothing more: it is as good as the labels, which are the person's word, and it says nothing of what the method would do on other data. With no labels nothing is scored or ranked, as before.
- **What is not used.** A `bakeoff.json` that is not in the shape that is kept (a limit or an amount spent that is not an amount, a method of a paper that is not a DOI or a link, one that a search found with no words of a model or one that the person added with some, an address of code that is not at a host that holds code, a page where a paper was found that is not one of Europe PMC's or arXiv's, what stands in the way of a method that is not one of the four, a step that is not one of the steps, a reason that is empty or too long, what the data is that a scope check would not take, right answers that are not a file's name with the name of a column (or two different columns), or a going on whose key is not one) is not a bake-off, and is not listed. One that an earlier version kept (it has a `schema` of 1, 2, or 3) is read as it was, with nothing said of where the right answers are, and, for the first two, nothing said of the data and no one gone on with. A directory that is a link is not followed. A run that is not in the shape that is kept (a state that is not one of three, a reason that does not fit the state, a run that has no result, tool, data, or method where it ran, a commit that is not one, a fingerprint that is not a hash, a number that is not finite, a call that says a model chose it and has nothing of what the model proposed or the other way about, words of a model that are too long or have control characters in them, a `not_proposed` or `limit` that is of a call that was not a model's to propose, a file of more than 1 MiB, or a folder of runs or a file that is a link) is not used, and the method is shown as one that was not run. A run that an earlier version kept (it has a `schema` of 1) is read as a run of the person's call.

**How far this has been checked.** That the words that a model said it went by are in the abstract that was shown, and that every number a model picked was of a paper that it was shown; and, of a method that is built, what a PaperAgent's steps check of it (see above), which is that its tools give again what its tutorials got, and no more. Not that the abstract says what the model took it to, that the method does the task, that it works on the person's data, or that it is better than another. Of a run, that this call was made to this code on this data, and what it gave, and not that what it gave is right.

## What it does not do yet

- It does not find a paper that is not open access, or is behind a login or a payment: it says so, and a file has to be uploaded. It does not try other sites for it.
- It builds Python environments only (pip and conda), from files that are in the code. The verdict on the code, before anything is built, is from the files alone. Of what is built, only the code's own tutorials are run (in Python), and only to keep what they did.
- It runs Python tutorials only, offline, within the limits above. It does not run the tutorials in R, Julia, or the shell, and it does not say that what a tutorial gave is right. It runs the code's own tests only to check a tool, only those that name its function as it imported it, and only with `pytest` if the environment has it. Those tests are of the code and not of the tool.
- It fetches data from seven places only (above), and only the files a person chooses. Private or controlled data, a login, and a place that is not on the list are not fetched. It does not look inside the data, or say whether what was fetched is what the paper used.
- It fetches from the four hosts above by https, at a public address, for code that is public. Private code, a login, a Git server of one's own, and an address that is not a project's are not fetched.
- A run is held for the person only when the lead has put the data against the card, which it is told to do and is not made to: a run on data that was never put against the card goes on and says so. What is put against the card is what the lead said the data is, which a program compares with the card's words; nothing looks inside the data, and a run carries no link to the person's files, so the lead can describe one dataset and run a tool on another.
- It does not check what it reads against anything but the paper: a claim is what the authors say, not what is true, and the method card is a draft until a person has read and approved it, and an approval says that they read it, not that it is right.
- It makes tools from the calls of plain functions only. Methods, functions that take objects that are not plain data, and calls that rely on what a tutorial set up before them are not made into tools yet. A tool of tier A shows that it gives again what the tutorial got, which is not independent of the tutorial; one of tier B has also passed checks against two of: the code's own function for changed inputs (made by a rule, or chosen by a model of another family, and these two are one), the code's own tests of that function in the environment (those do not call the tool), and giving a number that the paper reports for the arguments of its tutorial (where a model said that the paper's sentence is about that place, and only a number with digits enough, in a result that is plain data, is looked for), which is more, and still does not show that what it gives is right. - It holds the paper's numbers to what the tutorials gave as they ran here, and no more: not to the paper's own data unless a tutorial used it, not to a number in a figure or a table that no tutorial printed, and not to a claim that is not a plain number. A model judges, from words alone, which place of what the tutorials gave a sentence is about. It names where a claim that did not reproduce first parts from the paper, and the differences that were found, and does not say that any is why; it does not see a default that a call was not given, nor a data version (only whether data was given), it keeps a different test or threshold that a person asks for beside a claim's own result, as a variant, and only for a claim held to a call of a function that can be called alone (see Variants); it gives the claims and the variants as tables to save (see Tables); it shows the trying, the differences, and the variants on the page.
- A conversation that is given an agent can read its paper's words and run its tools, and nothing else of it. The paper is searched by words and not meaning, a tool is called one call at a time (nothing is kept from one call to the next), and the lead is told, and not made, to say where the paper says a thing and to leave a result unchecked. A scientist that speaks for a paper in a team session is told to speak from the paper alone, with the tools, and to say where, and it is not made to; it knows nothing of the paper until it calls a tool. The comparison of two papers' claims is by words and numbers, which marks places to read and does not say that papers disagree, and the kinds of files are read from docstrings and names and not from files, so a tool that says nothing is not checked, and what one tool gives is not passed to another by the lab: each call is one call, in a container of its own.
- The check of data against the card is of what the person or the lead says the data is, and nothing looks in the data to see. It knows a short list of names that mean one thing (some species, assays, tissues, and formats) and otherwise compares words, so a name it does not know, that means what one on the card says, is called outside, which is a warning and not a stop. It compares sizes only against a range or a bound, and only for the same thing counted. The lead is told to check before it runs a tool on the person's own data, and is not made to.
- A paper with no code can have a function written from its words, which is checked against the numbers the paper reports and no more, and is given to conversations only once it matched one. The page shows what the model would be given, asks for the agreement before anything is sent, and shows the function, its code, what it was checked against, and the inputs that a person gives for a claim.

The schedule works while the server runs, and the page of an agent does not show how it is or the schedule: the API does.
- The graph of papers (see [The graph of papers](#the-graph-of-papers)) is made by matching names, addresses, numbers, and words, and not by meaning: a dataset or method that two papers call by names that are not alike is not found, a claim in other words is not set against another, a paper is found to name another only if its facts and claims say its DOI, code address, name, or title (not from its list of references, which is not read), and which of the four ways it names it is told by the words next to the name. Nothing is asked of a model or of the web, so a paper that no agent is made of is not in it, and the page of the agents does not show it: the API and the lead's tool do.
- Author and reviewer mode (see [Author and reviewer mode](#author-and-reviewer-mode)) reads what the steps kept and runs none of them: the person starts the fetch, the build, the tutorials, the reading, and the trying of the numbers, each of which it names when it was not done. It looks at no more than 40 papers of a triage, each of at most 200 megabytes (50 left out), lists bioRxiv by date and subject (at most 300 preprints) with the abstracts that the listing gives, and does one triage at a time. - A bake-off finds and builds methods, puts what the person says of their data against each method's card, and runs a tool of each on their data. The call is the person's or a model's (which a program checks as it checks theirs, and which sees the data's place and not what is in it, and only the first 15 tools of a method), only the latest run of a method is kept, and the data is told to be as it was by its names, sizes, and times and not by what is in it. Its page takes a call as typed JSON and not as a form for each parameter, shows a missing Docker as a message with no button to set it up, and what the data is is typed by the person and not worked out from the Data page, and a candidate that an arXiv search found is read from its PDF, which is only possible when the PDF has text. A method is built only if its paper is, and its code is, in the places that a PaperAgent can have them from, and only from Python code with tutorials: a method with none says why and is left out.
